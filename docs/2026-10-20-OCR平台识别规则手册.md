# OCR 平台识别规则手册

> 适用代码：`cloudfunctions/api/ocr.js`（纯逻辑，可 Node 直接测试）
> 规则版本：`OCR_RULE_VERSION = 2026-10-31.4`
> 前端构建版本：`BUILD_VERSION = 2026-10-31.3`
> 测试：`node scripts/verify-models.js`（621 项）、`node scripts/verify-project.js`（68 项，含「文档与实现字段一致性」「裸跳转」「组件零引用」校验）

---

## 0. 三条铁律

1. **平台判定靠「品牌词 + 入口 + 字段组合」，不靠订单号长度、前缀、页面配色。**
2. **证据不足返回 `unknown`，不猜。** 只有通用词（订单号/退款/售后/服务单）时不判平台。
3. **OCR 结果是建议值**，前端只回填 `high/medium` 置信度；用户核对后保存。

---

## 1. 调用链与输出

```
识别图片 → 腾讯云 GeneralBasicOCR → rawText
        → analyzeOrder(rawText) → { platform, platformConfidence, pageKind,
            productName, amount, amountLabel, date,
            orderNo, orderNoLabel, orderNoIsFallback,
            returnNo, returnNoLabel, returnReason, pickupCode, pickupTime,
            statusRaw, statusKey, evidence, ruleVersion }
        → api 云函数透传（含 ocrVersion）
        → order-edit.applyOcrResult() 回填
```

- `ocrVersion` / `ruleVersion` 用于确认云端是否已重传；前端 Console 会打印。
- `evidence` 记录命中的平台证据，便于排查。

## 2. 平台判定表

> `detectPlatform()` 的检查顺序很重要：快手 → 抖音 → 唯品会 → 苏宁 → 京东 → 天猫 → 淘宝 → 拼多多 → 美团/饿了么/小红书。**天猫必须在淘宝前。**

| 平台 | high（强证据） | medium（仅品牌/弱入口） |
|---|---|---|
| 淘宝 | 我的淘宝/已买到的宝贝 + 退款编号或退款处理中；88VIP / 闲鱼转卖 / 退货宝 | 仅出现「淘宝」 |
| 天猫 | 天猫客服 / 要求天猫客服介入 / 天猫超市 / 天猫国际 / 退款编号 / 退款详情 | 仅出现「天猫」 |
| 京东 | 京东/我的京东 + 服务单号 +（进度查询或退换/售后） | 仅出现「京东/我的京东」 |
| 苏宁易购 | 我的易购/苏宁 +（服务单或进度查询） | 仅出现「苏宁」 |
| 拼多多 | **兔喜生活**（包裹代收品牌）；拼多多 + 退款/售后/售后详情/商家处理中 | 仅出现「拼多多」 |
| 抖音电商 | 抖音商城/抖音电商/抖音；**来自豆包 / 豆包App** | 仅出现「抖音」；或弱组合「交易完成 + 买后必看/再买一单」 |
| 快手小店 | 快手小店/快手 + 售后 | 仅出现「快手」 |
| 唯品会 | 唯品会 + 退货详情/快递员已取回/取件时间/仓库验货；或「退货详情 + 取件/验货」无品牌 | 仅出现「唯品会」 |
| 美团/饿了么/小红书 | — | 仅品牌词（medium） |
| unknown | 只有订单号/退款/售后/服务单等通用词 | — |

**易混淆对**
- 天猫 vs 淘宝：天猫优先；「天猫旗舰店」这种店铺名不单独作为强证据。
- 京东 vs 苏宁：两者都用「服务单 + 进度查询」，必须叠加「我的京东」/「我的易购」。
- 抖音 vs 快手：必须有品牌或「豆包/快手小店」入口；不靠订单号长度。
- 拼多多 vs 快手：优先「兔喜生活 / 退款/售后聚合入口」。
- 唯品会 vs 淘宝：唯品会看「退货详情 + 快递员已取回/取件时间」，淘宝看「退款编号/取件码」。

## 3. 页面类型 `pageKind`

- `aftersale_detail`：退款详情、退货详情、售后详情、退款编号、退款单号、售后单号、服务单号、售后申请单号、退款处理中、退货退款、退款成功、已退款。
- `order_detail`：订单详情、订单编号、订单号、下单时间、实付款、实付金额、实付、交易成功。
- `unknown`：都没有。

## 4. 编号标签（先标签、后取值）

### 订单编号 `orderNo`
`订单编号、订单号码、订单号、交易订单号、交易单号、淘宝交易单号、订单ID、order_id、orderId`

兜底：命中「订单信息 / 复制」时取 12–24 位数字串（淘宝常见「订单信息 共7项 3316… 复制」）。

### 售后编号 `returnNo`
`退款编号、退款单号、售后单号、售后申请单号、服务单号、售后编号、退货单号、退货编号、退货码`

### 归一化 `normalizeOrderNo`
- 全角 → 半角
- 去掉所有空白
- 截断 64 位（`validate` 会先拦截超过 64 位）
- 查库时同时查 `orderNo` 与旧字段 `returnNo`

### 订单号兜底
没有「订单编号/订单号」时，用售后号兜底填 `orderNo`，并置 `orderNoIsFallback = true`。
原因：退货页截图往往只有「退货单号」，不兜底就无法查重。

## 5. 金额 `amount`（单位：分）

优先级：
`退款金额 > 实付金额 > 实付款 > 实付 > 应付总额 > 订单金额 > 合计 > 商品金额`

规则：
- 同行/下一行取金额；
- 跳过「减/省/优惠/立减/折扣/抵/券/返/运费/税」上下文；
- 兜底也跳过优惠/运费行；
- **先用后付**：实付为 0 且文本含「先用后付/先享后付/货到付款」时，取「…付款¥9.7」的应付金额，标签记 `先用后付-应付`；没有则取第一个非零金额，标签 `先用后付-商品价`。

`amountLabel` 会返回命中的标签，便于排查。

---

## 6. 收货日期 `date`

严格标签：
`收货日期、收货时间、签收日期、签收时间、到货日期、到货时间、确认收货时间、确认收货`

规则：
- 标签同行或下一行取值；
- 下一行必须**以年份开头**，避免「预计送达 2026-10-08」被采纳；
- 含「预计」的行直接跳过；
- 没有标签时，若文本含「已签收/已领取/已送达」，取页面第一个日期（拼多多物流页常见）；
- **不拿下单时间/预计送达冒充收货日**。

---

## 7. 售后状态 `statusRaw` / `statusKey`

优先级（取最靠后的阶段）：
`refunded > return_received > return_in_transit > failed > closed > processing > approved > pending_seller`

映射：
- 退款成功/已退款/退款完成/退款已到账 → `refunded`
- 商品退仓/仓库验货/退货已签收/商家已签收 → `return_received`
- 快递员已取回商品/已取回商品/已取件/退回中 → `return_in_transit`
- 退款失败 → `failed`
- 已关闭/撤销售后/拒绝退款/商家拒绝 → `closed`
- 退款处理中/退款中/待退款 → `processing`
- 审核通过/商家已同意/同意退货/卖家已同意 → `approved`
- 等待商家处理/商家处理中/待商家处理/等待卖家处理 → `pending_seller`

`statusRaw` 保留页面原文。

## 8. 取件字段

- `pickupTime`：取件时间/预约取件时间/上门取件时间/上门时间/预约时间；也识别「等待…上门取件」文案，保留原文 40 字。
- `pickupCode`：只认「取件码/取件号/上门取件码/寄件码」；**「退货码」不算取件码**；标签后是「复制」时返回空。

## 9. 商品名清洗管线（顺序不可乱）

1. `cleanProductName`：去行尾价格（`¥105 x1`）、去尾部箭头（`∨/⌄/˅/∧/⌃`）。
2. 逐行过滤：
   - 纯金额 / 日期 / 数字 / 太短；
   - 字段与按钮：订单、快递、运费、合计、实付、应付、收货、退货、退款、售后、服务单、进度查询、取件、物流、店铺、客服、优惠、申请时间、下单时间、商品金额、钱款去向；
   - 状态：待收货/待发货/待付款/已完成/交易成功/**交易完成/交易关闭**/退款成功/处理中/等待商家/商家处理/审核通过/退款中/已退款/七天无理由/无理由/仅退款/退货退款/撤销/拒绝；
   - 物流：已签收/待签收/派送中/运输中/已发货/待评价/已评价；
   - 收件人/地址/手机号：`****` 脱敏号、真实手机号（`1[3-9]xxxxxxxxx`、`182-1234-5678`）、先生/女士/收货人、小区/号楼/单元/室/街道/号院/城区/镇/村；
   - 促销/UI/店铺：收集进度/拆盒后可/好评率/进店逛逛/价格明细/优惠解析/店铺优惠/共减/交易快照/共X项/来自豆包/豆包App/服务保障/买后必看/操作使用指南/使用指南/分享商品/再买一单/申请售后/联系商家/删除订单/追加评价/查看物流/更多信息/运费险/退换货自动理赔/快件/收件人/已领取/兔喜生活/号码保护/消费提醒/购后小助手/售后详情/承诺达/准时送达/商品快照/发生争议/可作为判断依据；旗舰店/专卖店/专营店/食品店/杂货铺/铺子/商贸/超市/便利店/小店/店铺/官方店；
   - 角标：`新1`、`新品2`（1–2 个汉字 + 1–3 位数字）、`系列+1`；
   - 纯编号（6–40 位字母数字下划线横线）、全大写短代号（GG7/NTP/88VIP）；
   - 平台/入口文案；
   - 店铺名 lookahead：下一行是好评率/进店逛逛/88VIP/粉丝/关注；
   - 收件人 lookahead：下一行是脱敏号/真实手机号。
3. 选行：
   - 中文行直接作为候选；
   - 纯英文商品名要求**含小写字母**、总长 ≥6、且含空格或 ≥8 位（避免 GG7 这类代号）；
4. 续行拼接：
   - 下一行是中文 4–40 字、无价格/字段/状态/平台词；
   - 首行以 `…` / `...` 结尾时视为标题被截断，允许续行带 `【】（）`；
   - 但「美乐蒂【拆盒未拆袋】」这类 **`汉字 + 【` 变体行不拼**；
5. 截断：`MAX_PRODUCT_NAME_LENGTH = 60`（与录入页 maxlength 60 一致）。

## 10. 置信度与前端回填

- `high`：品牌 + 平台专属字段/入口组合，或唯一强组合（如唯品会退货进度链）。
- `medium`：只出现品牌词，或窄组合（如「交易完成 + 买后必看」→ 抖音）。
- `unknown`：只有通用词。
- 前端只回填 `high/medium` 且平台名在 `PRESET_PLATFORMS` 内；否则不填。

## 13. 已知坑（都踩过）

1. **OCR 文本顺序 ≠ 视觉顺序**：UI 文案可能先于商品标题出现，必须过滤，不能只取第一个中文行。
2. **手机号正则过宽**：`\d{3,}[-*]\d{2,}` 会把「100-150斤」当电话，导致标题整行被跳过；已收紧为真实手机号/脱敏号。
3. **先用后付实付 0**：不能直接把 0 当金额，要取「付款 ¥X」。
4. **短角标**：「新1」「新品2」不是商品名。
5. **标题截断**：首行以 `…` 结尾时允许拼带规格括号的续行，但「汉字+【」变体行不拼。
6. **退货页只有退货单号**：必须兜底填 `orderNo`，否则查重静默失效。
7. **云端未重传**：代码改了不重传 `api`，线上仍是旧规则；用 `ocrVersion` / 设置页构建版本确认。
8. **平台无品牌文字**：返回 unknown，让用户手选；不要用订单号长度猜。
9. **寄回详情页没有商品名文本**：商品名在缩略图里，OCR 文本只有进度条（「寄回商品」）、寄件服务说明、地址、费用——这些行最像商品名。已整组过滤，宁可不填让用户手填。
10. **取件码不一定是 6 位**：拼多多预约成功页的取件码是 4 位（如 2281）。标签命中不受位数影响；6 位数字兜底只对无标签页面生效。
11. **相对日期不能进取件时间**：「明天09:00-11:00」这类带「今天/明天/后天/上午/下午」的句子不填，字段要的是绝对时刻。
12. **截图混入系统 UI（相册权限横幅）**：拍图时微信弹「"拼多多"仅可访问部分照片 / 现在如需修改其照片访问范围请前往设置。」。**它是一整块，不是一行**——OCR 常把正文拆成「现在」+「如需修改…」两行，前者只有两个字，对任何过滤词都免疫，会先被选中再被跨行拼接缝成一句。按行加词表修不掉，必须按区块剔除（`stripPhotoPermissionBanner`，锚点 + 前后碎行 + 正文 + 按钮，遇价格/脱敏号/地址即停，最多 6 行）。碎行长度上限只能取 **3 字**：取 6 会把「观赏鱼杀菌盐」这类 6 字真商品名吞掉，商品名退化成前一行「现在」。
13. **商品卡营销角标**：`「全新升级第七代` 这类角标会被 OCR 读成「引号 + 文字」，比真标题更靠前。判据是「剥行首引号后行首命中营销词且 ≤12 字」或「整行就是第X代」——**不能用「包含」匹配**，否则真标题「品牌第七代]亚甲基蓝热带鱼金」会被一起跳掉（2026-10-31 实测踩过）。
14. **完整句子不是标题**：以中文句号「。」结尾的行既不能当商品名，也不能当标题续行。同一条判据要同时用在两处，只用在续行处的话，锚点一丢正文行仍会被选成商品名。
15. **价格行会插进标题两行之间**：OCR 按 Y 坐标排序，价格在卡片右侧时会落在标题上下两行之间。拼接时要跳过这一行再看下一行，但**只在标题确实被截断时**才跨行续接（候选行以省略号收尾，或首行已截断）——不加这个前提，商品卡下方小图里的文字会被拼进标题。
16. **无品牌字的订单页靠底部按钮定平台**：「再次拼单」是拼多多独有（淘宝/京东「再次购买」、抖音「再买一单」），单条即给 `pdd · mid`。mid 已够回填表单；low 不够，`api/index.js` 只认「pdd 且非 low」。

## 15. 取件码识别（按平台分发）

> 版本：`2026-10-24.1`。入口：记一笔/编辑页顶部的「拍订单截图，自动填」。

### 15.1 为什么单独做一套

订单页 OCR 里已有的 `extractPickupCode()` 只在「取件码标签 + 值」清晰时才出结果。
拼多多上门取件页有个常见形态：**标签被折叠/截断，页面上只剩一串 6 位数字**。
这时旧逻辑返回空，用户只能手抄。所以补一层兜底，并用置信度区分。

### 15.2 判定顺序（`resolvePickupCode`）

| 顺序 | 形态 | 置信度 | source |
|---|---|---|---|
| 1 | 「取件码 / 取件号 / 上门取件码 / 寄件码」标签同行或换行取到值 | `high` | `label` |
| 2 | 全文扫描 6 位数字，取离标签行最近的那个 | `low` | `regex` |
| 3 | 都没有 | `''` | `''` |

- 第 1 步的值要过 `looksLikePickupCode()`：去空格后长度 ≤ 24 且**至少含一个数字**。
  否则「取件码 → 请向快递员出示」这类说明文字会被当成码，给出假的 `high`。
- 第 2 步的 `PICKUP_CODE_RE = /\b\d{6}\b/g`：带 `\b` 边界，8 位以上的订单号不会被截成 6 位。
- 距离用行号差；距离相同取靠前的，保证结果稳定可测。

### 15.3 平台分发（预留接口）

```js
getPickupCodeByPlatform(text, platform)  // 本期 platform === '拼多多' 才走实现
```

其他平台**一律返回空**，由前端提示手填——不在这一版里猜别的平台规则。
后续加平台：在这一个函数里加分支 + 补真实页回归，调用方不用改。

### 15.4 输出与置信度闸门

云函数 `api` 的 `ocrOrder` 返回：

```js
{ raw_lines, pickup_code, order_no, confidence, need_confirm }
```

`need_confirm = (confidence !== 'high')`，即**只要不是标签命中，就必须让用户核对**。
这是「识别 → 用户确认 → 再写入」的闸。

### 15.5 边界

- 回填走编辑页既有通道 `applyOcrResult()`：**只填空的取件码输入框，不覆盖用户已填内容**；
  编辑页本身就是「识别 → 用户核对 → 保存」，满足「识别 → 确认 → 写入」。
- `need_confirm`（6 位数字兜底）时，识别完成提示改为「已识别，请核对取件码」点名核对。
- 记一笔的识别截图超过 5MB 先 `wx.compressImage`（quality 70），压缩失败用原图继续。
- 前端不持有任何密钥；OCR 密钥只在云函数环境变量里。

### 15.6 结构化抽取通道（`pickup-extract.js`，2026-10-28.3）

> 与 15.1–15.4 的既有通道**并存不冲突**：既有 `pickup_code` / `pickup_confidence` /
> `need_confirm` 语义保持不变；新通道结果放在 `pickup` 对象里，前端命中时优先用它。

抽取顺序（固定，不可调换）：

1. **定页型**：关键词加权，内部桶 `待取件 > 取件码展示 > 选方式 > 订单详情 > 申请成功 > 物流`；
   `退货申请成功/已提交` 属无码页，直接 `has_pickup_code=false`。
   输出时映射成 schema 的四个值：`order_detail / after_sale_detail / pickup_code_page / unknown`
   （选方式页与申请成功页都归 `after_sale_detail`；物流页在 schema 里没有对应值，归 `unknown`）。
2. **定位置**：码必须①紧跟 `取件码/提货码/取件口令` 标签（同行→下一行），或②在 `复制`/二维码旁且上下文有取件码语义。
3. **排除干扰**：订单号、退货/售后单号、运单号、手机号、年份、日期不作码值；
   单号/地址/金额行（`订单号|运单号|商家地址|取件地址|实付|金额|预估费用|运费`）里的数字
   在**三条取值路径**（同行、下一行、复制旁、邻近兜底）上都要挡住。
4. **OCR 错识**：`raw` 原样保留；`normalized` 只做 `O/o→0`、`l/I→1`；
   区块 `score<0.6` 或有字符断裂（单字符被空白拆开、码值由多个区块拼成）时 → `normalized` 留空 + `low_confidence=true`。

输出 11 个字段（严格按 schema），缺值一律空串，不给 null：

```js
{ platform, platform_conf, page_type, has_pickup_code,
  pickup_code_raw, pickup_code_normalized, low_confidence,
  order_sn, express_company, pickup_time, address }
```

字段取值约束：

| 字段 | 约束 |
|---|---|
| `platform` | 透传 15.7 闸门的英文平台码，未传时为 `unknown` |
| `platform_conf` | 透传闸门置信档 `high/mid/low`，未传时为 `low` |
| `page_type` | `order_detail` / `after_sale_detail` / `pickup_code_page` / `unknown`（内部 6 桶映射，见上） |
| `pickup_code_raw` / `pickup_code_normalized` | raw 原样；normalized 只做 `O/o→0`、`l/I→1`；`low_confidence=true` 时 normalized 留空 |
| `express_company` | **只认「快递公司/承运/物流公司」标签行**，不扫全页；订单页自然抽不到即留空（该页只有代收点，进「查看物流」才有承运商） |
| `order_sn` | 保留连字符原样，如 `261011-360343170593024` |
| `pickup_time` / `address` | 标签值原样返回，不做日期推断 |

四条硬约束：
- **无标签也不在复制/二维码旁 → 判「没有取件码」，不猜**（不做全页数字扫描）。
- **不凭「像取件码」补字符**，字符断裂时宁可给空 normalized 让用户看原图。
- **带连字符的长编号不切段**：`261015-521320568353024` 两侧数字属同一串，`261015` 不能单独成 token。
- **非 pdd 或闸门置信不足 → 不跑邻近兜底**，命中码也强制 `low_confidence=true`。
- **码值 4~6 位、不含连字符**：含「-」的一律是订单号；允许 OCR 混淆字符 `O/o/l/I` 先入，再由 `normalizeCode` 归一（否则「O128→0128」永远走不到）。
- **旧通道同样标签绑定**：`ocr.js` 的 `findPickupCodeFallback` 在页面没有「取件码」标签时直接返回空，不做全页数字扫描。

已知取舍：既有通道的「6 位数字兜底」仍在（历史行为），新通道更严格；
两者冲突时前端以新通道为准，仅当 `has_pickup_code=true`。

**旧通道字段在非拼多多平台上恒空**（2026-10-31 补充）：
`index.js` 返回的 `pickup_code` / `confidence` / `pickup_confidence` / `need_confirm`
都来自旧通道 `ocr.analyzeOrder`，而旧通道的取件码只实现拼多多分支
（`getPickupCodeByPlatform` 对其他平台返回空）。所以在抖音等平台上：

| 字段 | 抖音页实际值 |
|---|---|
| `pickup_code` | `null` |
| `confidence` / `pickup_confidence` | `""` |
| `need_confirm` | `false` |

真实取件码只在 `pickup.pickup_code_raw` / `pickup.pickup_code_normalized` 里。
**新代码一律读 `pickup.*`**；旧字段保留只为不破坏既有调用方。

### 15.7 第 0 步平台闸门（`platform-gate.js`，2026-10-28.2）

所有字段抽取前先定平台：`platform` 取 **英文码** `pdd / taobao / jd / express / unknown`，
`platform_conf` 取 `high / mid / low`。既有中文字段 `platform`（拼多多/淘宝…）保持不变，
两者并存：闸门决定「用哪档规则」，中文字段仅供表单回填。

判定顺序（命中即返回，不叠加）：

| 顺序 | 信号 | 结果 |
|---|---|---|
| 1 | 拼多多品牌词（拼多多/PDD/百亿补贴/拼多多退货/拼多多官方取件） | pdd · high |
| 2 | **淘宝系品牌词**（我的淘宝/已买到的宝贝/淘宝/天猫/88VIP/退货宝） | taobao · high |
| 3 | **京东品牌词**（我的京东/京东）；仅「服务单号+进度查询」 | jd · high / jd · mid |
| 4 | 拼多多专属组件 ≥2 条（寄回商品/撤销售后/月卡专享/寄件详情/本次寄件服务享受官方补贴/请在快递员上门后出示/待快递员取件/拼多多退货服务协议/兔喜生活/兔喜） | pdd · high |
| 5 | 快递壳子（顺丰速运/菜鸟裹裹/运单详情…）**且无电商业务词** | express · high/mid |
| 6 | 短信截图落款【】+退订 | 按落款定 pdd/taobao/jd，其余 unknown |
| 7 | 微信壳子无业务方 | unknown · low |
| 8 | 退货单号特征（26/24 开头长数字，含连字符格式，或 PP/PDD 前缀） | pdd · high |
| 9 | 专属组件 1 条 | pdd · mid |
| 10 | 组件信号（上门取件/退款进度/售后详情）≥1 条 | pdd · high（2026-10-28 规则列为强信号） |
| 11 | 弱信号 ≥2 组（取件码 / 待取件 / 快递员接单 / 极兔·韵达 / 订单编号 / 订单号格式） | pdd · low |
| 12 | 其余（含只有「取件码」一条） | unknown · low |

> **顺序即隔离**：竞争平台品牌词（2、3）必须排在「拼多多专属组件」（4）之前。
> 反例（2026-10-28 实测并修复）：淘宝页只因含「撤销售后 / 寄件详情」两条拼多多专属组件，曾被判成 pdd·high。

两条与需求原文不同的处理（有依据，非随意改）：

1. **`上门取件 / 退款进度 / 售后详情` 按需求方 2026-10-28 规则升为强信号**（`COMPONENT_AS_STRONG = true`）。
   竞争平台品牌词在更前面判断，所以淘宝/京东页不会被它抢走；无品牌词的唯品会/苏宁页可能误判为 pdd，属已知取舍。
   **「订单编号」降为弱信号**（单独不算，需 ≥2 组），与 `YYMMDD-15位` 订单号格式同组。
2. **新增「拼多多专属组件」一组信号**。依据：`docs/2026-10-24-拼多多售后页平台识别要素.md` 的 A 级要素。
   没有这组，真实「预约成功页」没有品牌词、只有专属文案，会判成 unknown——即用户 10-24 报的那个问题。

规则档位 `mode`：

- `full`：`platform=pdd` 且 `conf≠low` → 取件码三条路径全开（标签 / 复制·二维码 / 邻近兜底）
- `label_only`：其他情况 → 只做通用标签直取，**关闭拼多多专属的邻近兜底**；命中码时 `low_confidence=true`

闸门结果同时回填既有中文字段：当 `analyzeOrder` 判不出平台而闸门为 `pdd` 且非 low 时，
`platform` 补为「拼多多」、`platformConfidence` 取 high/medium；其他平台不抢既有结论。

## 16. 多平台规则隔离约定（底线）

> 用户 2026-10-28 明确：**以后其他平台的识别规则也要更新，但不同平台的规则一定不要混淆，这是底线。**

### 16.1 三层结构

| 层 | 内容 | 允许跨平台 | 代码位置 |
|---|---|---|---|
| L0 平台判定 | 品牌词、专属组件、壳子、单号格式 | 否（每个信号必须挂明确平台） | `platform-gate.js` |
| L1 通用规则 | 标签绑定、位数、归一化、干扰项排除、**码值与日期/时间粘连的切分** | **是**（平台无关的锚点才可共用） | `code-split.js`（切分）；`pickup-extract.js` 的 `CODE_LABELS` / `NUMBER_OWNER_LINE_RE` / `normalizeCode` |
| L2 平台专属规则 | 专属关键词、专属兜底、专属页码型 | 否（必须按平台命名空间隔离） | `platform-gate.js` 的 `PDD_EXCLUSIVE` 等；`ocr.js` 的 `getPickupCodeByPlatform` 分发 |

**判定权归属**：L2 只能在 L0 判为该平台后生效；L1 可以服务所有平台。
**禁止**：把 L2 的词写进 L1 的共用常量（例如把「寄回商品」塞进 `CODE_LABELS`）。

### 16.2 新增一个平台的必做清单

1. **独立一节**：在本手册新增 `<平台>识别规则` 一节，不与拼多多混在同一段描述里。
2. **独立信号组**：在 `platform-gate.js` 新建该平台的专属常量（如 `TAOBAO_EXCLUSIVE`），**不复用** `PDD_EXCLUSIVE`。
3. **独立分发**：`ocr.js` 的 `getPickupCodeByPlatform` 增加该平台分支；其他平台仍返回空。
4. **独立真实样本**：至少 2 张该平台的真实截图（一张有码、一张无码），存进 `scripts/verify-models.js` 的回归段。
5. **独立回归用例**：在该平台小节下断言「本平台判定 / 本平台出码 / 本平台不套拼多多规则」三类。
6. **隔离用例**：交叉断言——该平台页面不得被判成 pdd，拼多多页面不得被判成该平台。
7. **台账登记**：在当日 `docs/YYYY-MM-DD-OCR识别修改记录.md` 按 `date/target/version/changed/reason/verify/keep_or_revert` 逐条记录。
8. **必查「码值与日期/时间粘连」**（用户 2026-10-31 明确要求，跨平台通用）：
   - 该平台取件码页面上，码后面是否紧跟日期/时段（如 `11月1日`、`11:00`）？
   - **必须用「故意去掉空格」的文本跑一遍**：OCR 会把原图里的小间隙合并，转写样本看不出这个问题。
   - 接入方式统一调 `code-split.js` 的 `splitCodeAfterLabel(tail)`，**不要**在平台文件里另写一套切分。
   - 断言该平台下：粘连日期取对码值、`low_confidence=true`、有空格时不标低置信、真 6 位码不被截断。
   - 参照测试段：`取件码切分通用规则（L1，跨平台共用）`、`拼多多通道接入 L1 切分`、`抖音取件码切分（码与日期粘连）`。

### 16.3 冲突裁决顺序（任何平台都适用）

```
本平台品牌词 > 其他平台品牌词 > 本平台专属组件 > 通用壳子/短信/微信 > 单号格式 > 组件信号 > 弱信号
```

理由：品牌词是唯一能证伪其他平台判定的证据。**竞争平台品牌词必须排在「某平台专属组件」之前**——否则会重演 2026-10-28 的淘宝页被拼多多文案抢走的事故。

### 16.4 现已接入的平台

| 平台 | 判定来源 | 专属规则 | 取件码 | 样本 |
|---|---|---|---|---|
| pdd | `platform-gate.js`：品牌词 / 专属组件 / 兔喜 / 退货单号 / 订单号格式 | `PDD_EXCLUSIVE`、邻近兜底、专属页型加权 | 出（标签绑定，4~6 位） | 5 张真实截图 + 2 页转录 |
| taobao | 品牌词（我的淘宝/已买到的宝贝/淘宝/天猫/88VIP/退货宝） | 暂无 | 仅通用标签路径，强制低置信 | 1 张（目录 `拼多多.jpg` 实为淘宝） |
| jd | 品牌词；或「服务单号 + 进度查询」 | 暂无 | 仅通用标签路径，强制低置信 | 0 张真实截图 |
| express | 快递壳子（且无电商业务词） | 暂无 | 不出（壳子页无取件码） | 0 张真实截图 |
| 唯品会 / 苏宁 / 抖音 / 快手 / 美团 / 饿了么 / 小红书 | 仅 `ocr.js` 旧 `detectPlatform` 有中文判定；闸门未接 | 暂无 | — | 仅旧合成样本 |

> 尚未接入闸门的平台，一律 `unknown`，**不得**套用拼多多的任何 L2 规则。

## 17. 取件码与日期粘连的切分规则（`code-split.js`，2026-10-31.4）

> 触发问题：2026-10-31 真机实测，抖音售后页取件码 `0131` 被填成 `013111`，且 `low_confidence=false`，没有任何核对提示。
>
> **本节规则不属抖音专属**：拼多多通道同样中招（`取件码2281 11月1日` 丢空格后变 `228111`）。
> 因此判据已抽到平台无关的 L1 模块 `cloudfunctions/api/code-split.js`，
> 抖音与拼多多共用；以后接入新平台**一律调这个模块，不要另写一套**（见 §16.2 第 8 步）。

### 17.1 问题成因

原图那一行是：

```
退货进度 取件码0131 11月1日(明天)上门取件
```

图上 `0131` 与 `11月` 之间**有**间隙，但微信 OCR 输出的文本里**没有**（用户 Console 的 `rawText` 实测为 `退货进度取件码013111月1日(明天)上门取件`）。

旧实现用 `CODE_RE = /[0-9OolI]{4,6}/` **贪婪匹配**，取满 6 位 → `013111`（把日期的 `11` 吃进来）。三道守卫全部放行：

| 守卫 | 为什么没拦住 |
|---|---|
| 码后不得紧接字母数字 | `月` 是中文，不算字母数字 |
| 长度 4~6 位 | `013111` 正好 6 位 |
| 低置信标记 | 只在区块分低或字符断裂时置真，标签命中路径恒 `false` |

连带影响：`pickup_time` 取自码后面的剩余文字，码多吃了 2 位，时间就少了 2 位（`月1日(明天)上门取件`）。

### 17.2 修复思路：多候选 + 剩余文字可否解析（已封装为 `code-split.js`）

**不能改成非贪婪 `{4,6}?`** —— 那会永远只取 4 位，把真实 6 位码（急速快寄等）截成 4 位，等于把一类错换成另一类错。

改为：先抓标签后**整段连续数字**（`DIGIT_RUN_RE`），再对 4/5/6 位候选逐一比较，用「切掉码之后的剩余文字能否构成完整日期/时间」定夺。

`restKind()` 四种分类：

| 类型 | 判据 | 例子 | 含义 |
|---|---|---|---|
| `full` | 以完整日期/时间开头（`1~12月`、`1~31日/号`、`0-23:00-59`） | `11月1日…`、`11:00…` | 切在这里是对的 |
| `eaten` | 以 `月/日/号/时/分/秒/冒号` 开头 | `月1日…`、`:00…` | 码把日期数字吃掉了 |
| `digits` | 数字开头但不成日期时间 | `15 明天…` | 码被切短了，该取更长 |
| `neutral` | 其它（空串、中文开头） | `明天上门取件` | 码就是整串 |

选法（按优先级）：

1. 存在 `full` 候选 → 取**最短的那个**（cands 按长度升序）；若数字串比它长 → `ambiguous=true`
2. 否则存在 `eaten` 候选 → 取最短候选，`ambiguous=true`
3. 否则数字串 >6 位 → 判为订单号/运单号片段，**不出码**
4. 否则（`neutral` / `digits`）→ 取整串，`ambiguous=false`

### 17.3 效果对照

| 输入（OCR 原文） | 修前 | 修后 | 低置信 |
|---|---|---|---|
| `取件码013111月1日(明天)上门取件` | `013111` | **`0131`** | true |
| `取件码013111:00上门取件` | `013111` | **`0131`** | true |
| `取件码38291511月1日上门取件` | `38291511` → 判空 | **`382915`** | true |
| `取件码382915 明天上门取件` | `382915` | `382915` | false |
| `取件码0131 11月1日…`（有空格） | `0131` | `0131` | false |
| `取件码12345678` | `123456` | **判无码** | — |

### 17.4 两条新增硬约束

- **`ambiguous=true` 时 `pickup_code_normalized` 留空**，与拼多多通道一致：宁可让用户看原值，也不给「修正过但可能错」的值。前端 `_pickupNeedConfirm` 会因此提示核对。
- **数字串超过 9 位直接判无码**（6 位码 + 最多 3 位日期是上限）。7~9 位只有在能切出完整日期时才出码，否则视为订单号/运单号片段。

### 17.5 回归样本

三个测试段共 44 项断言，两端分别覆盖：

| 测试段 | 覆盖对象 | 项数 |
|---|---|---|
| `取件码切分通用规则（L1，跨平台共用）` | `code-split.js` 本身 | 13 |
| `拼多多通道接入 L1 切分` | 拼多多是否真的调了 L1 | 7 |
| `抖音取件码切分（码与日期粘连）` | 抖音 + 用户真实 rawText 50 行 | 24 |

其中「拼多多通道接入 L1 切分」这组是**专门防「只修一端」**的：把拼多多里的 L1 调用改掉，这 7 项里会红 4 项，而抖音段仍全绿——两端各自独立可证伪。

> 教训：之前的抖音测试样本是**人工按截图转写**的，视觉上有缝隙就敲了空格，而真实 OCR 不保留。以后新增 OCR 样本必须**故意不加空格**写一版，模拟 OCR 输出。

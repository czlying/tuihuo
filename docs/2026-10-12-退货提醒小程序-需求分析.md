> 版本：v1.1（架构评审修订版）  
> 日期：2026-10-12  
> 状态：已修订，待开发  
> 形态：微信小程序（Taro/uni-app）+ 腾讯云开发 CloudBase 后端  
> 修订说明：v1.0 → v1.1 修正了 5 处内部矛盾与 3 处架构隐患，详见文末《附录 B：v1.1 架构评审修订记录》

## 1. 背景与问题

### 1.1 现状
- 用户日常在多个购物平台（淘宝/天猫、京东、拼多多、抖音电商、唯品会、美团/饿了么等）分散消费，"先用后买""冲动下单""凑单满减"导致**待退货订单数量激增**。
- 各平台退货政策不同（7 天无理由、15 天质保、生鲜不支持等），**退货时效窗口各异**。
- 订单散落在不同 App，用户缺乏统一视图；**"该退的忘了退，钱白花/货压箱底"**是高频抱怨。
- 微信生态内缺少一款"聚合式退货待办 + 智能提醒"的轻量工具。

### 1.2 核心痛点
1. **信息分散**：退货订单跨多个平台，无统一清单。
2. **时效易忘**：退货窗口只有几天，过期即丧失权利。
3. **进度失控**：申请了没寄、寄了没退款、退款延迟，状态不透明。
4. **金额漏算**：待退金额、已退金额没有汇总，不知道"被占用"了多少钱。

### 1.3 产品定位（一句话）
> 一款帮"多平台剁手党"把**待退货订单聚到一起、算清时效、到点提醒、跟踪进度**的退货管家小程序。

## 2. 目标与范围

### 2.1 产品目标
- 提供**跨平台退货订单的统一收纳与看板**。
- 基于各平台退货规则，自动计算**最晚退货时间**并**主动提醒**。
- 跟踪每笔退货的**全生命周期状态**，避免"退到一半断了"。
- 用数据让用户直观看到**待退/已退金额**与**逾期风险**。

### 2.2 v1 范围内（MVP）
- 退货订单导入：**手动录入 + 截图 OCR 识别**两种方式（OCR 识别后用户核对补全再保存）。
- 退货时效倒计时与**到期前推送提醒**（以微信订阅消息为主）。
- 退货天数规则：**用户录入"收货日期"，系统自动按"收货日 + 7 天"算出最晚可退日，支持手动修改**。
- 退货状态机（v1 仅到已申请）：**待退货 → 已申请 / 已逾期**。
- 首页看板：待退笔数、待退金额、本周到期、已逾期。
- 平台管理（增删常用平台）、基础统计。

### 2.3 v1 范围外（后续迭代）
- 各平台**官方 API 自动同步订单**（受平台开放能力限制，短期不可行）。
- 退货状态向后延伸：已寄出 → 退款中 → 已完成（v1 止于"已申请"）。
- 退款到账自动核对（需对接支付流水，敏感）。
- **跨端独立 App 并上架苹果 App Store**（见 §9、§12，需前端采用跨端框架）。
- 社交/多人共享、家庭账本。

## 3. 目标用户与角色

| 角色 | 描述 | 核心诉求 |
|------|------|----------|
| 主力用户 | 25–40 岁、多平台高频网购人群 | 别让我忘退、别让我逾期 |
| 轻度用户 | 偶尔退货、嫌麻烦的人 | 录入越简单越好（截图即可） |
| （未来）家庭管理员 | 帮家人管理退货 | 多账号/共享清单 |

**使用场景举例**
- 深夜剁手后，随手拍一张订单截图，小程序自动提取"商品/下单日/平台/金额"，算出最晚可退日，并设置提醒。
- 周末收到"3 天后到期"推送，集中处理几笔待退订单。
- 月底看板：本月待退 ¥860，已退 ¥1,240，有 1 笔逾期——立刻补退或放弃。

| 维度 | 各平台自带"退换/售后" | 记账类 App | 本小程序 |
|------|----------------------|------------|----------|

| 退货时效提醒 | ⚠️ 部分有 | ❌ | ✅ 倒计时+推送 |
| 进度跟踪 | ✅ 平台内可见 | ❌ | ✅ 跨平台统一 |
| 录入成本 | — | 高（逐条手填） | 低（截图 OCR） |

> 差异化核心是**"跨平台 + 时效提醒 + 低录入成本"**三件事的组合，单看每一项都有替代品，组合后形成壁垒。

## 5. 功能需求（详细）

### 5.1 订单导入
- **F-1 手动录入**：商品名、平台、**收货日期**、金额、退货规则（7/15 天）、凭证图。
  > 注：日期字段统一为**收货日期**，是全篇唯一的计时基准（§2.2 / F-5 / §8 均以此为准）。v1 不采集"下单日期"，避免两套日期口径导致 deadline 歧义。
- **F-2 截图 OCR 识别（v1 实现）**：上传订单截图，调用 OCR 提取关键信息（商品/金额/日期/平台），用户**核对并补全**后保存；识别结果不强依赖准确率，`source` 标记为 ocr，原始文本存 `ocrRaw` 备查。
- **F-3 平台选择/新增**：从常用平台库选择，或自定义平台名称。
- **F-4 批量导入**：连续拍多张截图，逐条解析后批量确认。

### 5.2 时效与提醒
- **F-5 自动算时效**：用户录入**收货日期**，系统按 `最晚可退日 = 收货日 + 7` 自动计算；结果**默认可改**，用户可手动调整天数或日期（覆盖个别平台 15 天/特殊规则）。
- **F-6 倒计时展示**：列表与详情显示"还剩 N 天 / 已逾期"。
- **F-7 订阅消息提醒**：到期前按用户配置的天数推送（`settings.remindAdvanceDays`，默认 `[3, 1, 0]` 即提前 3 天、1 天、当天各推一次；依赖用户授权订阅消息）。
  > **规则优先级**：用户设置 > 系统默认。`remindAdvanceDays` 为去重后的天数数组，`0` 表示当天提醒。同一订单同一档位**只推一次**，由 `lastRemindStage` 字段保证幂等。
- **F-8 智能时机**：避免在深夜推送；可设置"提醒时间段"（`settings.quietHours`），命中免扰时段的推送顺延到时段结束后首次运行。

### 5.3 状态跟踪（v1 仅到"已申请"）
- **F-9 状态机流转（v1）**：待退货 → 已申请；超过最晚可退日未操作则标记为**已逾期**。
- **F-10 节点记录**：录入时记录收货日期与最晚可退日；点击"已申请"后写入 `appliedAt` 时间戳与备注，形成简易时间线。
- **F-11 异常提示**：已逾期订单在首页/列表标红，提示"已丧失无理由退货权利，可尝试平台申诉"。

### 5.4 看板与统计
- **F-12 首页看板**：待退笔数/金额、本周到期、已逾期、本月已退金额。
- **F-13 筛选排序**：按平台、状态、到期时间排序；支持"只看逾期"。
- **F-14 月度统计**：已退/待退金额趋势（可选图表）。

### 5.5 个人与设置
- **F-15 平台管理**：常用平台增删、退货天数默认值。
- **F-16 提醒设置**：是否开启推送、提醒提前天数、免扰时段。
- **F-17 数据导出**：导出退货清单（便于对账）。

## 7. 关键业务流程（文字流程）

```
录入订单(手动 或 截图OCR识别) → 核对补全 → 填收货日期 → 自动算最晚可退日(可改)
        ↓                                    ↓
   加入待退清单 → 首页看板更新        写 uid / source / ocrRaw
        ↓
  [定时云函数] 每日 08:00 扫描 status=pending
        ↓
  命中 remindAdvanceDays 档位 且 lastRemindStage 未覆盖 → 推送订阅消息 → 更新 lastRemindStage
        ↓
  用户看到提醒 → 点击"已申请"更新状态 → 写入 appliedAt
        ↓
   看板统计待退金额 / 逾期标记
```

**状态机（v1）**
```
待退货 ──用户标记已申请──▶ 已申请
  │
  └──────── 超过最晚可退日且未申请 ────────▶ 已逾期（仅提示，可尝试申诉）
```
（后续版本：已申请 → 已寄出 → 退款中 → 已完成）

## 8. 数据模型（CloudBase 集合草案）

**orders（退货订单）**
| 字段 | 类型 | 说明 |
|------|------|------|
| _id | string | 主键 |
| _openid | string | 所属用户（CloudBase 自动注入，作为安全规则校验字段） |
| uid | string | 业务用户 ID（跨端设计，见 §9.2；小程序端 v1 可与 _openid 同值） |
| platform | string | 平台名（关联 platforms.name） |
| productName | string | 商品名 |
| amount | number | 金额，**单位：分**（整数存储，避免浮点误差；展示层除以 100） |
| receiveDate | date | 收货日期（用户录入，**全篇唯一计时基准**） |
| returnDays | number | 退货天数，默认 7，可改 |
| deadline | date | 最晚可退日 = receiveDate + returnDays，可手动改 |
| status | string | 状态枚举: pending / applied / overdue |
| source | string | 录入来源: manual / ocr（**v1 两条通道均启用**，见下方修订说明） |
| ocrRaw | string | OCR 原始识别文本（source=ocr 时写入，供核对与后续调优，v1 已启用） |
| lastRemindStage | number | 已推送到的**档位阈值**（非剩余天数），用于 F-7 幂等去重。详见附录 C.5 |
| appliedAt | date | 标记"已申请"的时间（status=applied 时写入，用于时间线 F-10） |
| logisticsNo | string | 物流单号（v1 预留，状态止于"已申请"，当前恒为空） |
| voucher | array | 凭证图 url（云存储 fileID 数组） |
| remark | string | 备注 |
| createdAt / updatedAt | date | 时间戳 |

> **v1.1 修订**：v1.0 版本此处的 `source`/`ocrRaw` 注记为"预留，v1 均为 manual / v1 空"，与文末决策 1（v1 实现 OCR）及 §5.1 F-2 矛盾。现已统一为 v1 双通道启用。
> **新增 `appliedAt` 与 `lastRemindStage`**：原模型缺少"已申请"时间（F-10 时间线无数据可取）与提醒去重标记（F-7 会重复推送）。

**platforms（平台规则）**：name、defaultReturnDays、color、sort。系统预置，**只读共享**，不按用户隔离。

**userPlatforms（用户自定义平台，v1 新增）**：name、color、_openid。用户在 F-15 中自建的平台存这里，避免直接写入全局 platforms 影响他人。

**settings（用户设置，每用户一条）**：_openid、uid、remindAdvanceDays（number[]，默认 [3,1,0]）、quietHours（{start,end}）、subscribeFlag（boolean）、createdAt / updatedAt。

## 9. 技术架构

### 9.1 整体选型
- **前端**：采用**跨端框架（Taro / uni-app）**而非纯小程序原生，便于后续复用代码编译为独立 App 上架苹果 App Store（见 §12）。v1 先以微信小程序为目标端。
- **后端**：腾讯云开发 CloudBase（云数据库 + 云函数 + 云存储）。
- **OCR**：云函数调用腾讯云 OCR 服务；识别结果**人工核对**兜底。
- **提醒**：云函数定时触发器（每天 08:00）扫描 `orders` 中 `status=pending` 的记录，按 `deadline - remindAdvanceDays` 命中条件时发订阅消息。
- **权限**：数据库安全规则 `_openid == auth.openid`（仅 `orders` / `settings` / `userPlatforms` 三个用户维度集合生效；`platforms` 为全局只读，不设该规则）。

### 9.2 用户标识与跨端演进（v1 关键设计）
跨端规划带来一个**必须现在处理**的问题：`_openid` 是微信专属标识，编译成 iOS App 后不存在。若 v1 直接用 `_openid` 做业务主键，v2 上架 App Store 时需要做一次全量数据迁移。

**方案**：双标识并存 —— `_openid` 仅用于安全规则校验（自动注入，零成本），另设 `uid` 作为**业务用户主键**：
- v1 小程序端：`uid` 直接复用 `_openid`，无需注册流程。
- v2 独立 App：新增 `users` 集合承载 Apple 登录，`uid` 改为自增/随机 ID，与微信 `openid` 建立映射。
- 代价仅是多一个字段，换来 v1 阶段零迁移成本。

> 这是本次架构评审认定的**最高优先级项**。跨端既然写进 §12 路线图，就必须现在留字段，事后补的成本是全量数据重刷。

### 9.3 集合清单
| 集合 | 用户维度 | 安全规则 | 说明 |
|------|---------|---------|------|
| orders | 是 | `_openid == auth.openid` | 退货订单主表 |
| settings | 是 | `_openid == auth.openid` | 用户设置，每用户一条 |
| userPlatforms | 是 | `_openid == auth.openid` | 用户自建平台 |
| platforms | 否 | 只读 | 系统预置平台库 |
| users | 是 | v2 启用 | 跨端账号（v1 仅预留字段） |

### 9.4 需要索引的字段
`orders.deadline + status`（定时扫描）、`orders._openid`（列表查询）。规模变大后再评估，当前不强制。

### 9.5 已知技术约束
- **OCR 选型**：原 v1.0 提的 `wx.serviceMarket` 同屏 OCR 插件需在微信后台单独申请、依赖插件市场审核，返回结构不稳定。v1 改走**云函数调用腾讯云 OCR**（无需用户侧插件审核、计费清晰），同屏 OCR 降级为可选优化项。
- **订阅消息额度**：一次性订阅消息每授权一次仅可下发一次。v1 需在用户每次进入"订单详情/确认提醒"时重新引导授权，单次授权只覆盖一个档位。这是 F-7 的硬约束，交互上要避免"以为授权一次就能收三次"。
- **CloudBase 定时触发器**：需在控制台手动配置，不随代码部署。上线 checklist 必须包含该步骤，否则提醒功能静默失效。

## 10. 风险与约束
1. **数据获取受限**：各大平台无统一退货 API，v1 只能手动/OCR，录入成本是生死线——OCR 准确率与"一键补全"体验决定留存。
2. **提醒触达受限**：微信订阅消息需用户**主动授权**且受下发额度限制，v1 以订阅消息为主，需做好"授权引导"；应用内红点/角标兜底列入后续版本。
3. **隐私合规**：订单含消费行为数据，必须在隐私政策中明示并最小化收集。
4. **规则复杂**：不同平台、不同品类（生鲜/定制/虚品）退货规则差异大，v1 以"收货日+7 默认、用户可改"为基础，预留平台默认天数模板于后续版本。
5. **跨端主键锁定**（v1.1 新增）：`_openid` 与微信强绑定，直接做业务主键会导致 v2 上架 App Store 时全量迁移。已在 §9.2 用 `uid` 双标识方案规避，但需在 v1 编码时严格遵守，避免偷懒直接用 `_openid` 关联查询。
6. **OCR 依赖外部服务**（v1.1 新增）：腾讯云 OCR 为付费服务，需评估调用量成本；同屏 OCR 插件方案存在审核不确定性，不作为 v1 主链路。

## 11. 验收标准（v1）
- [ ] 用户可从 0 到 1 完成一笔订单录入（手动或截图）并看到倒计时。
- [ ] 到期前能收到至少一次订阅消息提醒（授权后）。
- [ ] 同一订单同一提醒档位**不会重复推送**（`lastRemindStage` 生效）。
- [ ] 状态可从"待退货"流转到"已申请"，逾期订单能正确标记；看板金额实时更新。
- [ ] 逾期订单在首页显著标记。
- [ ] 仅本人可见本人数据（安全规则验证通过）。
- [ ] 修改 `settings.remindAdvanceDays` 后，提醒档位随之变化（用户设置优先于默认值）。
- [ ] 所有集合均按 §9.3 配置了对应安全规则；`orders.uid` 已写入且非空。

## 12. 后续规划（路线图）
> 说明：此处版本号指**产品迭代版本**，与本文档自身的版本号（v1.1 文档修订）无关。

- **产品 v1.1**：OCR **精度优化**（针对各平台订单截图样式微调识别模板）+ 常用平台模板（一键带出默认天数）。
- **v1.2**：退货状态向后延伸到 已寄出 → 退款中 → 已完成；退款到账手动核对 + 逾期催办话术生成。
- **v2**：探索与个别平台开放能力对接（如订单导入授权），降低录入成本。
- **v2+（跨端）**：基于 Taro/uni-app 代码库编译**独立 iOS App 并上架苹果 App Store**，补齐账号体系（微信登录 + Apple 登录）、内购/订阅合规等。
- **更远**：家庭共享、年度"退货报告"等轻运营。

## 附录 C：编码阶段的设计细化（2026-10-12）

实现过程中对 §7 / §8 / §9 做了 5 处细化。这些不是推翻原方案，而是把原方案里含糊的地方落实成明确规则，**编码以本附录为准**。

### C.1 `overdue` 改为运行时派生，不落库

**原设计**：`status` 枚举含 `overdue`，由定时云函数扫描后写入。
**改为**：`status` 落库值只有 `pending` / `applied`；`overdue` 在每次读取时按 `deadline < today` 派生。

**理由**：
1. 定时任务与用户操作会竞争写同一个 `status` 字段，容易写出脏数据（用户刚标记已申请，定时任务又把它标成逾期）；
2. 定时任务一旦失败，状态与真实日期不一致，用户看到的就是错的；
3. 原 §7 状态机本来就注明逾期是「**仅提示**」，派生语义与之一致。

**影响**：§11 验收标准中「逾期订单能正确标记」依然成立，只是标记方式从「写库」变成「读取时计算」。派生结果每次都对，不会出现状态滞后。

### C.2 按天粒度的日期统一用 `'YYYY-MM-DD'` 字符串

**涉及字段**：`receiveDate`、`deadline`。
**带时刻的字段**：`appliedAt`、`createdAt`、`updatedAt`、`lastRemindAt` 仍用 `Date`。

**理由**：用户选的是「哪一天」，不含时刻。若存成 `Date` 会被转成 UTC，读回时可能因时区差**错开一天**（典型表现：选了 10 月 1 日，读出来是 9 月 30 日）。字符串形式既能按字典序正确排序、直接做区间比较，也彻底绕开时区问题。

### C.3 `platforms` 集合在 v1 实际不使用

预置平台改为小程序端本地常量（`constants/index.js` 的 `PRESET_PLATFORMS`），无需建集合。
**v1 只需创建三个集合**：`orders`、`settings`、`userPlatforms`。
`platforms` 集合保留为 v2 的平台模板（含 `defaultReturnDays` 差异化配置）的落点。

### C.4 云函数合并为 2 个

| 云函数 | 职责 |
|--------|------|
| `api` | 业务 API，用 `action` 路由复用（当前：`whoami`、`health`） |
| `timerRemind` | 定时扫描 + 提醒判定 + 订阅消息推送 |

**理由**：减少冷启动次数（云函数冷启动是小程序体验的主要损耗），且部署只需两次。内部按 handler 组织，后续动作变多再拆。

### C.5 提醒幂等语义：`lastRemindStage` 记录「已推到的档位阈值」

> **v1.2 修正**：原设计把 `lastRemindStage` 定义为「上次推送时的剩余天数」，
> 且用 `advanceDays.indexOf(remainDays) === -1` 精确相等判定档位。
> 代码审查发现这会导致**档位永久漏推**：某档当天若因免扰时段 / 未授权（43101）/
> 函数异常而跳过，次日剩余天数落在两档之间，精确相等匹配不上 → 该档位永远不推。
> 例：档位 `[3,1,0]`，剩 3 天当天被免扰跳过，次日剩 2 天，`indexOf(2) === -1` 直接跳过。

修正后采用**档位区间**模型：`advanceDays` 把「到期前时间轴」切成若干区间，
每个区间在**首次进入时**推一条，同一区间内不重复。

`lastRemindStage` 存的是**已推到的档位阈值**（区间上界），不是剩余天数。判定规则：

1. 计算当前所处区间的上界 `threshold` = 所有满足 `remainDays <= 档位值` 的档位中最小值；
2. `remainDays > 最大档位` → 尚未进入提醒期，不推；
3. `lastRemindStage` 为空（从未推过）→ 首次推送；
4. `threshold < lastRemindStage` → 进入了更晚的档位区间，**补推**；
5. 否则 → 同区间已推过，不重复。

**举例**（档位 `[3,1,0]`）：
- 剩 3 天，首次 → 推，记录 `lastRemindStage = 3`；
- 次日剩 2 天，`threshold` 仍为 3，`3 < 3` 不成立 → 不重复推；
- 次日剩 1 天，`threshold` 变 1，`1 < 3` 成立 → 补推「1 天档」，记录 `= 1`。

**写入顺序**：先发送、成功后再写 `lastRemindStage`。若写失败只可能重复推一次；反过来先写后发，发送失败就会**永久漏推**。

> **实现约定**：`decideRemind` 返回的 `stage` 是档位阈值（用于幂等写入），
> `remainDays` 是真实剩余天数（用于消息文案）。两者不可混用——
> 消息里显示「还剩 N 天」必须用 `remainDays`，用 `stage` 会在跳档时显示错误天数。

### C.6 新增的两个坑（已知问题，代码已处理）

| 坑 | 说明 | 处理 |
|----|------|------|
| **云函数时区是 UTC** | 腾讯云函数运行时默认 UTC，北京时间 08:00 触发时 `new Date().getDate()` 会拿到前一天 | `timerRemind` 内所有「今天」统一用 `todayInBeijing()`（+8 小时偏移）计算 |
| **小程序端单次查询上限 20 条** | 直接 `get()` 会静默丢数据，统计金额会少算 | 适配器提供 `listAll()` 自动翻页；凡需完整集合做统计的场景必须用它 |

### C.7 编辑保存必须用「变更集」语义

> **v1.2 新增**：代码审查发现，编辑订单保存时 `deadline` 会被静默清空。

根因：页面 `collectForm()` 用 `''` 表达"用户没手动改日期"，
而服务层 `update()` 用 `=== undefined` 判断是否重算 —— `''` 绕过重算分支，
又被日期归一化写成 `''` 入库。后果：订单不再判逾期、不进临期名单、定时提醒永久跳过，且无任何报错。

**约定**：
1. 页面产出的是**变更集**而非完整对象 —— **字段不存在 = 不修改**，禁止用 `''` / `null` 表达"没填"；
2. 服务层把 `''` 与 `undefined` 同等视为"未指定"（容忍历史写法）；
3. 纯逻辑层最后兜一道：空串一律不写库。

**实现落点**：字段处理逻辑抽到 `models/order.js` 的 `buildUpdatePatch()`，
`order.service.update()` 与测试脚本调用同一个函数 —— 不在测试里复刻逻辑，
否则改真实代码测试不会变红，等于没锁住。

同理，编辑态**不得携带 `source` 字段**，否则 OCR 录入的来源标记会被抹成 `manual`。

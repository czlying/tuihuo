## 1. 背景与问题

### 1.1 现状
- 用户日常在多个购物平台（淘宝/天猫、京东、拼多多、抖音电商、唯品会、美团/饿了么等）分散消费，"先用后买""冲动下单""凑单满减"导致**待退货订单数量激增**。
- 各平台退货政策不同（7 天无理由、15 天质保、生鲜不支持等），**退货时效窗口各异**。
- 订单散落在不同 App，用户缺乏统一视图；**"该退的忘了退，钱白花/货压箱底"**是高频抱怨。
- 微信生态内缺少一款"聚合式退货待办 + 智能提醒"的轻量工具。

### 1.2 核心痛点
1. **信息分散**：退货订单跨多个平台，无统一清单。
2. **时效易忘**：退货窗口只有几天，过期即丧失权利。
3. **进度失控**：申请了没寄、寄了没退款、退款延迟，状态不透明。
4. **金额漏算**：待退金额、已退金额没有汇总，不知道"被占用"了多少钱。

### 1.3 产品定位（一句话）
> 一款帮"多平台剁手党"把**待退货订单聚到一起、算清时效、到点提醒、跟踪进度**的退货管家小程序。

## 2. 目标与范围

### 2.1 产品目标
- 提供**跨平台退货订单的统一收纳与看板**。
- 基于各平台退货规则，自动计算**最晚退货时间**并**主动提醒**。
- 跟踪每笔退货的**全生命周期状态**，避免"退到一半断了"。
- 用数据让用户直观看到**待退/已退金额**与**逾期风险**。

### 2.2 v1 范围内（MVP）
- 退货订单导入：**手动录入 + 截图 OCR 识别**两种方式（OCR 识别后用户核对补全再保存）。
- 退货时效倒计时与**到期前推送提醒**（以微信订阅消息为主）。
- 退货天数规则：**用户录入"收货日期"，系统自动按"收货日 + 7 天"算出最晚可退日，支持手动修改**。
- 退货状态机（v1 仅到已申请）：**待退货 → 已申请 / 已逾期**。
- 首页看板：待退笔数、待退金额、本周到期、已逾期。
- 平台管理（增删常用平台）、基础统计。

### 2.3 v1 范围外（后续迭代）
- 各平台**官方 API 自动同步订单**（受平台开放能力限制，短期不可行）。
- 退货状态向后延伸：已寄出 → 退款中 → 已完成（v1 止于"已申请"）。
- 退款到账自动核对（需对接支付流水，敏感）。
- **跨端独立 App 并上架苹果 App Store**（见 §9、§12，需前端采用跨端框架）。
- 社交/多人共享、家庭账本。

## 3. 目标用户与角色

| 角色 | 描述 | 核心诉求 |
|------|------|----------|
| 主力用户 | 25–40 岁、多平台高频网购人群 | 别让我忘退、别让我逾期 |
| 轻度用户 | 偶尔退货、嫌麻烦的人 | 录入越简单越好（截图即可） |
| （未来）家庭管理员 | 帮家人管理退货 | 多账号/共享清单 |

**使用场景举例**
- 深夜剁手后，随手拍一张订单截图，小程序自动提取"商品/下单日/平台/金额"，算出最晚可退日，并设置提醒。
- 周末收到"3 天后到期"推送，集中处理几笔待退订单。
- 月底看板：本月待退 ¥860，已退 ¥1,240，有 1 笔逾期——立刻补退或放弃。

## 5. 功能需求（详细）

### 5.1 订单导入
- **F-1 手动录入**：商品名、平台、**收货日期**、金额、退货规则（7/15 天）、凭证图。
  > 注：日期字段统一为**收货日期**，是全篇唯一的计时基准（§2.2 / F-5 / §8 均以此为准）。v1 不采集"下单日期"，避免两套日期口径导致 deadline 歧义。
- **F-2 截图 OCR 识别（v1 实现）**：上传订单截图，调用 OCR 提取关键信息（商品/金额/日期/平台），用户**核对并补全**后保存；识别结果不强依赖准确率，`source` 标记为 ocr，原始文本存 `ocrRaw` 备查。
- **F-3 平台选择/新增**：从常用平台库选择，或自定义平台名称。
- **F-4 批量导入**：连续拍多张截图，逐条解析后批量确认。

### 5.2 时效与提醒
- **F-5 自动算时效**：用户录入**收货日期**，系统按 `最晚可退日 = 收货日 + 7` 自动计算；结果**默认可改**，用户可手动调整天数或日期（覆盖个别平台 15 天/特殊规则）。
- **F-6 倒计时展示**：列表与详情显示"还剩 N 天 / 已逾期"。
- **F-7 订阅消息提醒**：到期前按用户配置的天数推送（`settings.remindAdvanceDays`，默认 `[3, 1, 0]` 即提前 3 天、1 天、当天各推一次；依赖用户授权订阅消息）。
  > **规则优先级**：用户设置 > 系统默认。`remindAdvanceDays` 为去重后的天数数组，`0` 表示当天提醒。同一订单同一档位**只推一次**，由 `lastRemindStage` 字段保证幂等。
- **F-8 智能时机**：避免在深夜推送；可设置"提醒时间段"（`settings.quietHours`），命中免扰时段的推送顺延到时段结束后首次运行。

### 5.3 状态跟踪（v1 仅到"已申请"）
- **F-9 状态机流转（v1）**：待退货 → 已申请；超过最晚可退日未操作则标记为**已逾期**。
- **F-10 节点记录**：录入时记录收货日期与最晚可退日；点击"已申请"后写入 `appliedAt` 时间戳与备注，形成简易时间线。
- **F-11 异常提示**：已逾期订单在首页/列表标红，提示"已丧失无理由退货权利，可尝试平台申诉"。

### 5.4 看板与统计
- **F-12 首页看板**：待退笔数/金额、本周到期、已逾期、本月已退金额。
- **F-13 筛选排序**：按平台、状态、到期时间排序；支持"只看逾期"。
- **F-14 月度统计**：已退/待退金额趋势（可选图表）。

### 5.5 个人与设置
- **F-15 平台管理**：常用平台增删、退货天数默认值。
- **F-16 提醒设置**：是否开启推送、提醒提前天数、免扰时段。
- **F-17 数据导出**：导出退货清单（便于对账）。

### 5.6 待寄出倒计时（后续版本，F-18）

> 2026-10-21 用户提出并加入待办，**本轮不实现**。

**背景**：用户申请退货后往往不会立刻寄出，会拖几天；超过平台要求的寄出时限可能被关闭售后。现有「已申请」列表只记录状态，没有「最晚寄出日」和倒计时，覆盖不到这个真实痛点。

**四维评估**
| 维度 | 结论 |
|---|---|
| 可行性 | 可行。小程序端用日期差做倒计时，无需平台 API；新增 `shipDeadline` 字段即可。平台寄出时限不一致（常见 7 天，也有 10/15 天），默认 7 天、允许手动改。 |
| 难度 | 中。字段 + 表单 + 页签/分区 + 倒计时 + OCR 标签 + 旧数据兜底 + 测试，约 1–2 天；提醒接入再加 0.5–1 天。 |
| 对现有影响 | 数据模型加 `shipDeadline`/来源标记；复用现有 `pickupTime`；首页「已申请」分区改造；订单编辑页加字段；OCR 加「最晚寄出/请于…前寄出/上门取件时间」标签；定时提醒需新增独立档位字段，避免与退货到期提醒重复。旧 applied 订单需按 `appliedAt + 7` 兜底并标注「推定」。 |
| 必要性 | 高。直接防止「申请后忘记寄、错过平台时限」，是现有「已申请」列表没有覆盖的核心场景。建议做。 |

**MVP 范围**
1. 已申请订单增加 **最晚寄出日** `shipDeadline`（`YYYY-MM-DD`）与来源 `shipDeadlineSource`（auto / manual / ocr）。
2. 默认 `shipDeadline = appliedAt + 7 天`，用户可改；平台默认天数后续可配置。
3. 首页把「已申请」分区升级为「**待寄出**」：按 `shipDeadline` 升序，显示「还剩 N 天 / 今天截止 / 已超 N 天」，逾期红、临期黄。
4. 有 `pickupTime` 的订单显示「上门取件：…」；没有则不显示。
5. OCR 识别「请于 X 月 X 日前寄出 / 最晚寄出时间 / 上门取件时间」；识别不到由用户手填。
6. 旧 applied 订单没有 `shipDeadline`：按 `appliedAt + 7` 自动补，标记「推定」，用户可改。
7. 已取货（picked）保留为终态历史，不新增状态；MVP 不引入「已寄出」独立状态。

**验收标准**
- 待寄出列表按最晚寄出日排序，倒计时与颜色正确。
- 编辑页可改最晚寄出日，保存后列表即时更新。
- OCR 能回填最晚寄出日/上门取件时间；识别不到不报错。
- 旧 applied 订单有推定截止日，不会显示空白。
- 保存/查重/左滑删除等现有能力不受影响。

**暂不做（Phase 2）**
- 按平台配置默认寄出天数。
- 基于 `shipDeadline` 的订阅消息提醒（需独立 `lastShipRemindStage` 防重复）。
- 已寄出/运输中/退款中状态、自动预约上门取件、平台 API 对接。

**待定决策（建议）**
1. 「待寄出」是**改造现有已申请分区**还是新增独立页签？建议改造，避免两套列表重复。
2. 默认寄出天数统一 7 天，平台差异后续再做；是否现在加设置项？建议 MVP 先固定 7 天、允许单笔手改。
3. 旧数据兜底按 `appliedAt + 7`，标注「推定」；是否允许一键批量确认？建议后续再说。
4. 是否删除「已取货」？建议保留为历史终态，不删除。

### 5.7 想退货清单（F-19，2026-10-21 实现）

> 2026-10-21 语义调整：**想退货名单 = 未申请、看可申请截止；退货名单 = 已申请、看最晚发货**。新建未勾「想退货」直接进入退货名单（status=applied）。详见 D.41。

**背景**：有些商品收到了但还在犹豫要不要退，直接放进退货名单会显得「已经决定退」。需要一个更轻的「想退货」暂存区。

**四维评估**
| 维度 | 结论 |
|---|---|
| 可行性 | 可行。不新增状态，只加 `considering` 布尔字段；首页把待退拆成两组；不依赖云函数或平台 API。 |
| 难度 | 中低。1 个字段 + 看板拆分 + 首页分区 + 详情页开关 + 决定退按钮 + 测试，约 0.5–1 天。 |
| 对现有影响 | 数据模型加 `considering`（旧数据默认 false，无迁移）；`getDashboard` 拆分计数/金额；主退货名单与搜索只含已决定退；详情页新增开关；标记上门取件时自动清除；提醒逻辑不变（仍是 pending）。 |
| 必要性 | 中高。避免「还没想好就被当成已决定退」，同时不引入新状态机。建议做。 |

**实现**
- `considering` 布尔字段，默认 false；旧订单按 false 处理。
- 首页新增「想退货」分区：显示数量、金额、截止日/倒计时、缩略图；行内「决定退」把 `considering` 置 false，移回退货名单。
- 「退货名单」只显示 `considering=false` 的待退订单，计数/金额同步排除；搜索也只搜这组。
- 详情页在新建/待退状态显示「想退货」开关；保存后进入/离开想退货清单。
- 标记上门取件时服务层写 `considering=false`，避免已取件订单残留标记。
- 不做新状态、不做独立页签，保持现有状态机与提醒不变。

**测试**：`verify-models.js` 290 项全绿；构建版本 `2026-10-21.12`。

### D.41 想退货/退货名单语义重定义（2026-10-21）

**用户澄清**：
- 想退货名单：尚未申请退货的犹豫订单，最晚日期 = **可申请退货截止**。
- 退货名单：**已申请退货**的订单，最晚时间 = **最晚发货时间**。
- 只有新建订单时可以勾「想退货」；其他列表打开详情不再显示该开关。
- 想退货名单支持左滑删除。

**四维评估**
| 维度 | 结论 |
|---|---|
| 可行性 | 可行。想退货名单复用 pending；退货名单复用 applied；新增 `shipDeadline` 字段；不新增云函数。 |
| 难度 | 中。列表映射、创建分流、发货截止、旧数据兜底、计数与文案，约 0.5–1 天。 |
| 对现有影响 | 新建未勾想退货 → 直接 `status=applied`（行为变化）；`pending` 全部显示为想退货名单；`applied` 显示为退货名单；新增 `shipDeadline`（旧 applied 按 `appliedAt+7` 兜底）；提醒仍只覆盖申请截止，发货提醒未接。 |
| 必要性 | 高。现有列表语义与用户真实流程不一致，按澄清修正。建议做。 |

**实现**
- 首页顺序：**想退货名单（pending）→ 退货名单（applied）→ 已取货**。
- 想退货名单：显示可申请截止日期 + 时分秒；行内「决定退」确认后选取件时间，转入退货名单。
- 退货名单：显示「最晚发货」；`shipDeadline` 默认 `appliedAt + 7` 天；旧数据按 `appliedAt+7` 兜底。
- 新建：勾「想退货」→ pending/considering；不勾 → applied + appliedAt + shipDeadline，直接进退货名单。
- 详情页「想退货」开关**仅新建显示**；编辑已有订单不显示。
- 想退货名单沿用原待退列表的左滑删除。
- `markApplied` 写 `appliedAt`、`shipDeadline`、`considering=false`；撤销申请清 `shipDeadline`。

**测试**：`verify-models.js` 292 项全绿；构建版本 `2026-10-21.14`。

### D.42 首页 `orderModel is not defined` 修复（2026-10-21）

**现象**：首页显示「orderModel is not defined」，全部数据为 0，名单空白。

**根因**：`_mapAppliedRow` 新增了 `orderModel.calcDeadline` 兜底最晚发货日，但 `pages/index/index.js` 漏了 `require('../../models/order')`。刷新在映射已申请行时抛错，`setData` 未执行，页面只显示错误与 0 值；**数据库数据未丢失**。

- `verify-project.js` 新增静态检查：页面使用 `orderModel.` 必须真实 require `models/order`；含 2 项校验器自检（导入完整 / 漏导入报警）。

**验证**：`verify-models.js` 292 项；`verify-project.js` 44 项通过。

**构建版本**：`2026-10-21.15`（设置页底部可见）。

### D.43 决定退进入详情 + 漏导入反思（2026-10-21）

**需求**：点击「决定退」不直接流转，先进入详情，用户补录信息后再标记。

**实现**：
- 想退货名单行内「决定退」改为 `catchtap="onOpenOrder"`，打开订单详情。
- 详情页仍用「标记为上门取件」完成确认 + 选取件时间 + 转入退货名单。
- 删除首页已不再使用的快捷标记方法、取件时间浮层与组件注册，避免两套流程并存。

**反思（orderModel is not defined）**：
- 不是改动复杂，而是我在页面新增 `orderModel.calcDeadline` 调用时**漏了 require**。
- `node --check` 只查语法，不查未定义标识符；模型测试不加载页面；原 `verify-project` 只查 require 路径是否存在，没查「用了但没导入」。
- 已补 `verify-project` 的「页面使用 `orderModel.` 必须导入」检查 + 自检。
- 流程约束：页面新增模块调用先补 import，再写逻辑；改完必须跑 `verify-project`，不能只跑 `node --check`。

### D.45 水印宿主遮挡按钮修复（2026-10-21）

### D.46 水印遮挡全页点击的最终修复（2026-10-21）

## 7. 关键业务流程（文字流程）

```
录入订单(手动 或 截图OCR识别) → 核对补全 → 填收货日期 → 自动算最晚可退日(可改)
        ↓                                    ↓
   加入待退清单 → 首页看板更新        写 uid / source / ocrRaw
        ↓
  [定时云函数] 每日 08:00 扫描 status=pending
        ↓
  命中 remindAdvanceDays 档位 且 lastRemindStage 未覆盖 → 推送订阅消息 → 更新 lastRemindStage
        ↓
  用户看到提醒 → 点击"已申请"更新状态 → 写入 appliedAt
        ↓
   看板统计待退金额 / 逾期标记
```

**状态机（v1）**
```
待退货 ──用户标记已申请──▶ 已申请
  │
  └──────── 超过最晚可退日且未申请 ────────▶ 已逾期（仅提示，可尝试申诉）
```
（后续版本：已申请 → 已寄出 → 退款中 → 已完成）

| createdAt / updatedAt | date | 时间戳 |

> **v1.1 修订**：v1.0 版本此处的 `source`/`ocrRaw` 注记为"预留，v1 均为 manual / v1 空"，与文末决策 1（v1 实现 OCR）及 §5.1 F-2 矛盾。现已统一为 v1 双通道启用。
> **新增 `appliedAt` 与 `lastRemindStage`**：原模型缺少"已申请"时间（F-10 时间线无数据可取）与提醒去重标记（F-7 会重复推送）。

**platforms（平台规则）**：name、defaultReturnDays、color、sort。系统预置，**只读共享**，不按用户隔离。

**userPlatforms（用户自定义平台，v1 新增）**：name、color、_openid。用户在 F-15 中自建的平台存这里，避免直接写入全局 platforms 影响他人。

**settings（用户设置，每用户一条）**：_openid、uid、remindAdvanceDays（number[]，默认 [3,1,0]）、quietHours（{start,end}）、subscribeFlag（boolean）、createdAt / updatedAt。

## 9. 技术架构

### 9.1 整体选型
- **前端**：采用**跨端框架（Taro / uni-app）**而非纯小程序原生，便于后续复用代码编译为独立 App 上架苹果 App Store（见 §12）。v1 先以微信小程序为目标端。
- **后端**：腾讯云开发 CloudBase（云数据库 + 云函数 + 云存储）。
- **OCR**：云函数调用腾讯云 OCR 服务；识别结果**人工核对**兜底。
- **提醒**：云函数定时触发器（每天 08:00）扫描 `orders` 中 `status=pending` 的记录，按 `deadline - remindAdvanceDays` 命中条件时发订阅消息。
- **权限**：数据库安全规则 `_openid == auth.openid`（仅 `orders` / `settings` / `userPlatforms` 三个用户维度集合生效；`platforms` 为全局只读，不设该规则）。

### 9.2 用户标识与跨端演进（v1 关键设计）
跨端规划带来一个**必须现在处理**的问题：`_openid` 是微信专属标识，编译成 iOS App 后不存在。若 v1 直接用 `_openid` 做业务主键，v2 上架 App Store 时需要做一次全量数据迁移。

**方案**：双标识并存 —— `_openid` 仅用于安全规则校验（自动注入，零成本），另设 `uid` 作为**业务用户主键**：
- v1 小程序端：`uid` 直接复用 `_openid`，无需注册流程。
- v2 独立 App：新增 `users` 集合承载 Apple 登录，`uid` 改为自增/随机 ID，与微信 `openid` 建立映射。
- 代价仅是多一个字段，换来 v1 阶段零迁移成本。

> 这是本次架构评审认定的**最高优先级项**。跨端既然写进 §12 路线图，就必须现在留字段，事后补的成本是全量数据重刷。

### 9.3 集合清单
| 集合 | 用户维度 | 安全规则 | 说明 |
|------|---------|---------|------|
| orders | 是 | `_openid == auth.openid` | 退货订单主表 |
| settings | 是 | `_openid == auth.openid` | 用户设置，每用户一条 |
| userPlatforms | 是 | `_openid == auth.openid` | 用户自建平台 |
| platforms | 否 | 只读 | 系统预置平台库 |
| users | 是 | v2 启用 | 跨端账号（v1 仅预留字段） |

### 9.4 需要索引的字段
`orders.deadline + status`（定时扫描）、`orders._openid`（列表查询）。规模变大后再评估，当前不强制。

### 9.5 已知技术约束
- **OCR 选型**：原 v1.0 提的 `wx.serviceMarket` 同屏 OCR 插件需在微信后台单独申请、依赖插件市场审核，返回结构不稳定。v1 改走**云函数调用腾讯云 OCR**（无需用户侧插件审核、计费清晰），同屏 OCR 降级为可选优化项。
- **订阅消息额度**：一次性订阅消息每授权一次仅可下发一次。v1 需在用户每次进入"订单详情/确认提醒"时重新引导授权，单次授权只覆盖一个档位。这是 F-7 的硬约束，交互上要避免"以为授权一次就能收三次"。
- **CloudBase 定时触发器**：需在控制台手动配置，不随代码部署。上线 checklist 必须包含该步骤，否则提醒功能静默失效。

## 10. 风险与约束
1. **数据获取受限**：各大平台无统一退货 API，v1 只能手动/OCR，录入成本是生死线——OCR 准确率与"一键补全"体验决定留存。
2. **提醒触达受限**：微信订阅消息需用户**主动授权**且受下发额度限制，v1 以订阅消息为主，需做好"授权引导"；应用内红点/角标兜底列入后续版本。
3. **隐私合规**：订单含消费行为数据，必须在隐私政策中明示并最小化收集。
4. **规则复杂**：不同平台、不同品类（生鲜/定制/虚品）退货规则差异大，v1 以"收货日+7 默认、用户可改"为基础，预留平台默认天数模板于后续版本。
5. **跨端主键锁定**（v1.1 新增）：`_openid` 与微信强绑定，直接做业务主键会导致 v2 上架 App Store 时全量迁移。已在 §9.2 用 `uid` 双标识方案规避，但需在 v1 编码时严格遵守，避免偷懒直接用 `_openid` 关联查询。
6. **OCR 依赖外部服务**（v1.1 新增）：腾讯云 OCR 为付费服务，需评估调用量成本；同屏 OCR 插件方案存在审核不确定性，不作为 v1 主链路。

### 12.1 盈利路线（2026-10-19 新增）

> 核心判断：**v1 阶段不做任何变现，先验证「有人用、愿意留」**。工具类小程序过早变现会杀留存；本产品先靠 OCR 免费额度（1000 次/月，见 D.6）把录入成本压到接近 0，跑通留存后再谈钱。

> **主体前置约束（2026-10-19 核实）**：当前小程序为**个人主体（身份证注册）**，微信政策下**不能使用订阅消息、也不能开通微信支付**。因此路线 B（会员订阅）与路线 D（虚拟支付）在个人主体下**无法实现**，必须先把主体升级为**个体工商户 / 企业**（路线 E 卖能力若走微信收款同样受限）。在个人主体阶段，提醒只能走应用内（首页名单 + 角标），推送提醒属受限项。升级个体户后，订阅消息与微信支付方可启用。

按优先级排序的 5 条路线：

1. **A｜先验证有人用（0→1，当前阶段）**
   - 不接广告、不设付费墙，靠口碑 + 体验版（最多 90 名体验成员，见 §D.5）自然增长；
   - 目标指标：周留存、OCR 使用率、临期订单提醒实际触达率（订阅消息接入后）。

2. **B｜会员订阅（核心路线，最优先）**
   - 微信支付「连续包月/包年」订阅，合规且用户认知成熟；
   - 免费版保留核心（手动录入 + 基础提醒 + 有限 OCR 次数），会员解锁：
     - 无限订单数 / 多端同步（跨微信与后续 App）；
     - 高级统计、月度趋势图、数据导出（对应待办 F-14/F-17）；
     - 更高 OCR 额度 + 精准模板；
     - 免广告、优先客服。
   - 毛利高：会员费远大于 OCR 后付费成本（见 D.6 阶梯，月活千次级成本可忽略）。

3. **C｜广告（慎用，仅作兜底）**
   - 工具类用户对广告容忍度低，**不嵌信息流 banner**；
   - 仅可对免费用户开放「激励视频换 OCR 次数」（微信流量主），自愿观看，不伤体验。

4. **D｜虚拟支付 / 内购（门槛高，后期）**
   - iOS App 上架需走 Apple 内购合规，微信侧虚拟支付限制多，**v2+ 跨端阶段再评估**，不与订阅冲突时再做。

5. **E｜卖能力 / 定制开发（B 端变现）**
   - 把「OCR 识别 + 时效提醒 + 进度跟踪」能力打包，给小电商 / 二手商家做轻 SaaS 或定制小程序；
   - 属技术输出而非 C 端收费，适合有客户资源时顺手做。

**结论**：v1 只做 A；B 是长期主营收，C/D/E 依次为补充与延展。OCR 计费见 D.6，上线务必关闭后付费开关防失控。

## 附录 C：编码阶段的设计细化（2026-10-12）

实现过程中对 §7 / §8 / §9 做了 5 处细化。这些不是推翻原方案，而是把原方案里含糊的地方落实成明确规则，**编码以本附录为准**。

### C.1 `overdue` 改为运行时派生，不落库

**原设计**：`status` 枚举含 `overdue`，由定时云函数扫描后写入。
**改为**：`status` 落库值只有 `pending` / `applied`；`overdue` 在每次读取时按 `deadline < today` 派生。

**理由**：
1. 定时任务与用户操作会竞争写同一个 `status` 字段，容易写出脏数据（用户刚标记已申请，定时任务又把它标成逾期）；
2. 定时任务一旦失败，状态与真实日期不一致，用户看到的就是错的；
3. 原 §7 状态机本来就注明逾期是「**仅提示**」，派生语义与之一致。

**影响**：§11 验收标准中「逾期订单能正确标记」依然成立，只是标记方式从「写库」变成「读取时计算」。派生结果每次都对，不会出现状态滞后。

### C.2 按天粒度的日期统一用 `'YYYY-MM-DD'` 字符串

**涉及字段**：`receiveDate`、`deadline`。
**带时刻的字段**：`appliedAt`、`createdAt`、`updatedAt`、`lastRemindAt` 仍用 `Date`。

**理由**：用户选的是「哪一天」，不含时刻。若存成 `Date` 会被转成 UTC，读回时可能因时区差**错开一天**（典型表现：选了 10 月 1 日，读出来是 9 月 30 日）。字符串形式既能按字典序正确排序、直接做区间比较，也彻底绕开时区问题。

### C.3 `platforms` 集合在 v1 实际不使用

预置平台改为小程序端本地常量（`constants/index.js` 的 `PRESET_PLATFORMS`），无需建集合。
**v1 只需创建三个集合**：`orders`、`settings`、`userPlatforms`。
`platforms` 集合保留为 v2 的平台模板（含 `defaultReturnDays` 差异化配置）的落点。

### C.4 云函数合并为 2 个

| 云函数 | 职责 |
|--------|------|
| `api` | 业务 API，用 `action` 路由复用（当前：`whoami`、`health`） |
| `timerRemind` | 定时扫描 + 提醒判定 + 订阅消息推送 |

**理由**：减少冷启动次数（云函数冷启动是小程序体验的主要损耗），且部署只需两次。内部按 handler 组织，后续动作变多再拆。

### C.5 提醒幂等语义：`lastRemindStage` 记录「已推到的档位阈值」

> **v1.2 修正**：原设计把 `lastRemindStage` 定义为「上次推送时的剩余天数」，
> 且用 `advanceDays.indexOf(remainDays) === -1` 精确相等判定档位。
> 代码审查发现这会导致**档位永久漏推**：某档当天若因免扰时段 / 未授权（43101）/
> 函数异常而跳过，次日剩余天数落在两档之间，精确相等匹配不上 → 该档位永远不推。
> 例：档位 `[3,1,0]`，剩 3 天当天被免扰跳过，次日剩 2 天，`indexOf(2) === -1` 直接跳过。

修正后采用**档位区间**模型：`advanceDays` 把「到期前时间轴」切成若干区间，
每个区间在**首次进入时**推一条，同一区间内不重复。

`lastRemindStage` 存的是**已推到的档位阈值**（区间上界），不是剩余天数。判定规则：

1. 计算当前所处区间的上界 `threshold` = 所有满足 `remainDays <= 档位值` 的档位中最小值；
2. `remainDays > 最大档位` → 尚未进入提醒期，不推；
3. `lastRemindStage` 为空（从未推过）→ 首次推送；
4. `threshold < lastRemindStage` → 进入了更晚的档位区间，**补推**；
5. 否则 → 同区间已推过，不重复。

**举例**（档位 `[3,1,0]`）：
- 剩 3 天，首次 → 推，记录 `lastRemindStage = 3`；
- 次日剩 2 天，`threshold` 仍为 3，`3 < 3` 不成立 → 不重复推；
- 次日剩 1 天，`threshold` 变 1，`1 < 3` 成立 → 补推「1 天档」，记录 `= 1`。

**写入顺序**：先发送、成功后再写 `lastRemindStage`。若写失败只可能重复推一次；反过来先写后发，发送失败就会**永久漏推**。

> **实现约定**：`decideRemind` 返回的 `stage` 是档位阈值（用于幂等写入），
> `remainDays` 是真实剩余天数（用于消息文案）。两者不可混用——
> 消息里显示「还剩 N 天」必须用 `remainDays`，用 `stage` 会在跳档时显示错误天数。

### C.6 新增的两个坑（已知问题，代码已处理）

| 坑 | 说明 | 处理 |
|----|------|------|
| **云函数时区是 UTC** | 腾讯云函数运行时默认 UTC，北京时间 08:00 触发时 `new Date().getDate()` 会拿到前一天 | `timerRemind` 内所有「今天」统一用 `todayInBeijing()`（+8 小时偏移）计算 |
| **小程序端单次查询上限 20 条** | 直接 `get()` 会静默丢数据，统计金额会少算 | 适配器提供 `listAll()` 自动翻页；凡需完整集合做统计的场景必须用它 |

### C.7 编辑保存必须用「变更集」语义

> **v1.2 新增**：代码审查发现，编辑订单保存时 `deadline` 会被静默清空。

根因：页面 `collectForm()` 用 `''` 表达"用户没手动改日期"，
而服务层 `update()` 用 `=== undefined` 判断是否重算 —— `''` 绕过重算分支，
又被日期归一化写成 `''` 入库。后果：订单不再判逾期、不进临期名单、定时提醒永久跳过，且无任何报错。

**约定**：
1. 页面产出的是**变更集**而非完整对象 —— **字段不存在 = 不修改**，禁止用 `''` / `null` 表达"没填"；
2. 服务层把 `''` 与 `undefined` 同等视为"未指定"（容忍历史写法）；
3. 纯逻辑层最后兜一道：空串一律不写库。

**实现落点**：字段处理逻辑抽到 `models/order.js` 的 `buildUpdatePatch()`，
`order.service.update()` 与测试脚本调用同一个函数 —— 不在测试里复刻逻辑，
否则改真实代码测试不会变红，等于没锁住。

同理，编辑态**不得携带 `source` 字段**，否则 OCR 录入的来源标记会被抹成 `manual`。

### D.17 OCR 平台识别规则（2026-10-20）

> 完整平台判定表、字段标签、商品名清洗管线与「新增平台 Checklist」见 [`2026-10-20-OCR平台识别规则手册.md`](2026-10-20-OCR平台识别规则手册.md)。

**依据**：`国内主流电商平台订单与退款页面识别特征.md`（桌面调研文档）。

**文档准确性结论**：整体准确、且方法论克制——明确反对「靠订单号位数/固定前缀/页面配色」判平台，主张「品牌词 + 入口 + 字段组合」。需注意：
- 部分来源是二手材料（网易转载的 2024 淘宝售后设计复盘、百科、教程），只能证明字段存在，不能当线上版式承诺；
- 淘宝/天猫共用交易体系，本应用把两者分开，因此加了「天猫优先」判定；
- 快手 6–32 位是开放接口约束，**不作为 OCR 判平台的依据**；
- 仅「服务单号 + 进度查询」无法区分京东/苏宁，本实现要求叠加品牌或「我的易购」；
- 文档未覆盖美团/饿了么/小红书，本实现只做品牌词弱识别。

**实现（`cloudfunctions/api/ocr.js`）**：
1. **平台判定 + 置信度**：`detectPlatform()` 返回 `{ platform, confidence: high|medium|unknown, evidence[] }`。
   - 快手小店/抖音电商：品牌 + 售后入口 → high；
   - 唯品会：「唯品会 + 退货详情/快递员已取回/取件时间」或纯「退货详情 + 取件/验货」→ high；
   - 苏宁：「我的易购/苏宁 + 服务单/进度查询」→ high；
   - 京东：「京东/我的京东 + 服务单号 + 进度查询/退换售后」→ high；
   - 天猫：天猫/天猫客服/退款编号 → high，且优先于淘宝；
   - 淘宝：「已买到的宝贝 + 退款编号/退款处理中」→ high；
   - 拼多多：「拼多多 + 退款/售后/售后详情」→ high；
   - 只有「订单号/退款/售后」等通用词 → `unknown`，不猜。
2. **页面类型**：`detectPageKind()` → `order_detail | aftersale_detail | unknown`。
3. **编号分维度**：订单号（订单编号/订单号/交易单号）与售后号（退款编号/退款单号/售后单号/服务单号）分别用标签取值，带编号清洗（剔除「复制/查看」等按钮词）。
4. **金额按标签优先级**：退款金额 > 实付 > 应付 > 订单金额 > 合计 > 商品金额，避免抓原价。
5. **收货日期严格化**：只认「收货/签收/到货/确认收货」标签；**没有就不填**，不再拿下单/申请时间冒充收货日。
6. **状态**：保留原文 `statusRaw`，并映射 `statusKey`（pending_seller/approved/processing/refunded/failed/closed/return_in_transit/return_received）。
7. **取件时间**：识别「取件时间/预约时间」及「等待…上门取件」文案，保留原文。
8. **取件码**：只认「取件码/取件号/寄件码」标签，不把「退货码」当取件码。

**平台清单**：预置库新增 **快手小店**、**苏宁易购**（原清单缺这两个，文档覆盖）。

**前端**：只有 `platformConfidence` 为 `high/medium` 且平台在清单内时才回填，`unknown/low` 一律不填，避免误导。

**测试**：`verify-models.js` 增至 **234 项全绿**（新增 64 项：9 个平台判定、不可判定场景、编号/金额/状态/取件时间/日期/商品名、编号与日期误判防护、真实淘宝页回归）；已做**可证伪校验**（破坏平台判定，9 项用例变红后还原）。另做**三轮仿真页面冒烟 + 两张真实淘宝截图校准**，累计修掉多个商品名/金额误判；最终 8 个平台样本全部符合预期，0 异常。`verify-project.js` 35 项通过。

### D.26 性能优化：列表刷新与 OCR 耗时（2026-10-20）

**问题 1：预览图片关闭后列表刷新卡**
- 根因：`index.onShow` 每次都执行 `refresh()`，而 `refresh()` 并行拉 `getDashboard + listApplied + listPicked` 三路数据；`wx.previewImage` 关闭会触发 `onShow`，导致无数据变化也全量重拉，缩略图跟着重载。
- 修复：`app.globalData.ordersDirty` 脏标记。首页只在**首次显示**或**脏标记为 true** 时刷新；录入页保存、标记已申请、标记已取货、删除成功后置脏；预览关闭、取消返回、切后台回来都不再刷新。
- 效果：关闭预览不再发 3 路查询、不再重载缩略图；从录入页真正改完数据返回仍会刷新。

**问题 2：新建时 OCR 慢**
- 根因：串行三段——客户端上传云存储 → 云函数 `downloadFile` 下载并转 base64 → 调腾讯云 OCR；首次还有云函数冷启动。
- 修复：
  1. 云函数优先 `cloud.getTempFileURL` 拿到临时 HTTPS，用 OCR 的 `ImageUrl` 让腾讯云直接拉图，省掉「下载 + base64」一跳；URL 失败自动回退 base64。
  2. OCR client 改为模块级复用，避免每次调用重新初始化 SDK。
  3. 录入页 `onLoad` 预热 `api` 云函数的 `health` 动作，把冷启动提前到用户选图之前。
  4. 加载提示拆两段：`上传图片` → `识别中`，避免一直显示「识别中」却卡在上传。
- 未采用（按需再评估）：更高压缩比（可能伤 OCR 小字）、云函数预留实例（有成本）。

**测试**：282 项、35 项结构校验通过。

**构建版本**：`2026-10-20.12`（设置页底部可见）。

### D.33 详情页无法编辑/保存/标记修复（2026-10-21）

**现象**：详情页金额、日期无法修改，保存和标记按钮也无响应。

**根因**：取件时间组件一直挂载在详情页。虽然 `visible=false` 时内部浮层不显示，但组件宿主仍参与页面渲染，存在遮挡触摸的风险；同时组件首次挂载时可能来不及初始化。

**修复**：
- 首页与详情页的 `<pickup-time>` 改为 `wx:if="{{pickupPickerVisible}}"`，不需要时完全不挂载。
- 组件增加 `attached` 生命周期：宿主首次以 `visible=true` 挂载时主动 `init()`，避免选择器为空。
- 详情页金额、日期、保存、标记逻辑本身未改；修复后恢复可编辑。
- 取件时间组件事件改用兼容写法 `bindconfirm` / `bindcancel`，避免取消事件不触发导致遮罩残留。
- 首页/详情页增加 `onHide`：切后台或离开页面时强制收起取件时间层。

**构建版本**：`2026-10-21.6`（设置页底部可见）。

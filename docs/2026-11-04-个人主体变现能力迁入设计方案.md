## 结论先行

文章给了 4 条变现路径 + 1 条 AI 资源路径。对一个「个人主体、还没发布、没有付费墙」的退货提醒工具，**四条路径的优先级完全不一样**：

| 序 | 能力 | 一句话结论 | 建议 | 依赖 |
|---|---|---|---|---|
| P0 | **小程序成长计划**（10 亿 Token + 10 万生图 + 6 个月云开发环境） | 唯一「今天就能领、领了直接服务下一版 OCR 优化」的项 | **立即做** | 无（已有云开发环境需先确认归属） |
| P1 | **赞赏组件**（用户「喜欢开发者」，平台不抽成） | 零开发成本的第一笔收入 | **做** | 基础库升到 3.17.5+、找一个贴图号 |
| P2 | 原创保护（名称保护 / 抄袭封禁） | 不需要开发，发布前顺手占位 | **顺手做** | 无 |
| P3 | 广告（流量主门槛 500UV → 100UV） | 现在没有 100UV，开了也是零收入且破坏柔彩风 | **延后** | 备案发布 + UV 达标 |
| P4 | 虚拟支付（个人主体可收款） | 技术可行，但**当前没有可卖的付费墙** | **延后（有明确付费点再启动）** | 认证 300 元/年 + 备案 + 道具设计 |

**一句话：先领 AI 额度（P0），再挂赞赏（P1），别急着上支付和广告。**

理由：
- P0 直接命中项目下一个大版本（OCR 识别优化），10 亿 Token 等于把识别成本压到零；
- P1 是文章里唯一「平台不抽成 + 免开发 + 个人主体专属」的收益通道，成本一个组件；
- P4 虽然最像「正经生意」，但虚拟支付只能卖**虚拟道具**，本小程序目前所有功能都免费、订单数无上限，**没有能挂付费墙的地方**。硬加会毁掉工具体验。

## 一、文章要点（原文摘要）

文章标题《个人做小程序，更好变现了》，面向**个人开发者**和 **OPC（一人公司）**，宣布三块支持。

### 1.1 更好变现 —— 三条通道

**① 小程序赞赏组件**
- 页面出现「喜欢开发者」按钮，用户点击跳转开发者的**贴图**完成赞赏；有人喜欢后展示喜欢人数 + 头像墙。
- **平台对赞赏不抽成**。
- 开通方式：进入「微信开发者助手」小程序的赞赏模块 → 绑定本人的贴图号或公众号 → 发表一篇与小程序相关的贴图 → 支持免开发一键接入。
- 原文限定：**仅支持个人主体小程序**；建议在贴图里讲清小程序功能或创作经历，内容越丰富越容易获得赞赏。

**② 虚拟支付：个人主体也能收款**
- 条件：个人主体 + 服务类目包含「工具」+ **已完成认证和备案** → 后台申请开通，直接在小程序内收款。
- 文章称平台已把个人虚拟支付能力 **Skill 化**，可通过 WorkBuddy 等 Agent 工具快速接入。
- 官方指引：`developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment/person`

**③ 广告智能接入与诊断**
- 「广告智能接入」支持零代码：系统分析小程序页面，自动推荐广告位置和类型，在线预览、调整后确认即可上线。
- **流量主开通门槛从 500UV 降至 100UV**。
- 开通流量主后，「智能变现」页可看诊断报告，对照行业标杆的 ARPU（人均广告收益）、IPU（人均广告曝光次数）给建议和收益预估。

### 1.2 原创保护 —— 无需开发的被动能力

- **事前**：原创小程序爆火时，平台主动保护其名称和搜索结果，防相似名称蹭流量。
- **事中**：开放社区陆续推出官方维权指南；新增「功能混淆」治理规范，专项打击恶意仿照功能的小程序。
- **事后**：认定代码抄袭或恶意抄袭的，**直接封禁、没收违法所得、不支持整改申诉**（仅支持误判申诉）。

### 1.3 AI 支持 —— 小程序成长计划

- 面向全行业类目，所有小程序开发者均可申请。
- **单个小程序**可按活动规则领取：免费云开发环境 + **10 亿 Token 生文额度** + **10 万张生图额度**。
- 已验证支持 Hy4 Preview、DeepSeek 等指定模型。
- 申请入口：微信公众平台 → 行业能力 → 小程序成长计划。
- 数据：截至 2026-09-30 累计 7.8 万个小程序加入，个人开发者占比超 70%。

## 四、四个迁移方案

每个方案按项目硬规则做**四维评估**：可行性 / 难度 / 对现有影响 / 必要性，并给出做、不做或延后的建议。

---

### 方案 A：小程序成长计划（P0 · 立即做）

#### 它带来什么

10 亿 Token + 10 万生图 + 6 个月云开发环境，且**只允许在小程序和云函数里用** —— 这正好是「拍订单截图自动填」的天然位置。

#### 为什么这是本项目最高价值的一条

项目下一个大版本就是 OCR 识别优化（`cloudfunctions/api/ocr.js` + 平台识别规则手册）。现有链路的三个结构性成本，`deepseek-v4.1-flash` 能直接削掉：

| 现有痛点 | 具体表现 | AI 通道如何改变 |
|---|---|---|
| 只拿到文字行，语义靠自己拼 | `ocr.js` 抽字段、`pickup-extract.js` 做版面推断、`code-split.js` 处理「取件码与日期粘连」 | 直接把截图丢给模型，要求输出**结构化 JSON**（平台、商品名、金额、取件码、收货日、单号） |
| 每接一个平台要写一套 L2 规则 + 抓真实页回归 | 拼多多已做，抖音/淘宝/京东待做；规则手册已积累大量正则 | few-shot 示例替代部分正则，新平台回归样本量可下降 |
| 云函数装 OCR SDK + 维护 SecretId/SecretKey | `tencentcloud-sdk-nodejs-ocr` 依赖体积大，密钥要放环境变量 | 云开发 AI **无需任何密钥**，Token 从赠送额度扣 |

**关键点：`deepseek-v4.1-flash` 是三个可抵扣模型里唯一支持图片输入的**（hy4-preview、hy3 都不支持图片）。所以做图像识别只能用这一个。

#### 技术落点（下一版才动，本次不改）

两条路，二选一或都留：

**路 1：小程序端直连（推荐做主通道）**
- 新增 `miniprogram/services/ocr-ai.service.js`，用 `wx.cloud.extend.AI`
- 好处：绕开云函数 3 秒超时
- 代价：prompt 在前端可见（prompt 不是密钥，可接受；但等于公开识别策略）

**路 2：云函数内调用（做兜底/对照）**
- 在 `cloudfunctions/api/` 新增 `ocr-ai.js`，`index.js` 加一个 action（如 `ocrAi`）
- 必须先解决：**把 `api` 云函数超时从 3 秒改到 20 秒**。这个只能在云开发控制台手改（部署工具没有 timeout 参数）。

**必须保留的既有硬约束（不能被 AI 通道绕过）**
1. 双通道并行，不直接替换腾讯云 OCR：同一批真实截图跑两条路，逐字段比对，差异进人工核对清单。
2. `need_confirm` 语义不变：模型置信度不足照样让用户核对（现有规则是 `confidence !== 'high'`）。
3. 平台判定（L0 闸门）仍要显式输出，未接入的平台一律 `unknown`，不得套拼多多 L2 规则。
4. 回填只填空位、不覆盖已填。
5. 规则改动仍要递增 `OCR_RULE_VERSION` 并记台账。

#### 四维评估

| 维度 | 结论 |
|---|---|
| 可行性 | 高。官方 API 已就绪，个人主体可领，类目含「工具」符合活动范围 |
| 难度 | 中。报名是用户侧 3 分钟操作；代码侧是新增一条通道 + 双通道对比脚本 |
| 对现有影响 | 中。新增服务文件 / 可选新增云函数 action；现有 OCR 规则与测试不动 |
| 必要性 | **最高**。直接服务下一个大版本目标，且把识别成本压到零 |

**建议：立即做。** 但分两步：
1. 今天先完成**报名 + 额度到账 + 一次最小连通性验证**（发一张截图，能拿到 JSON 即可）。
2. 识别通道的工程化（双通道、结构化输出、回归样本）并入下一版 OCR 优化排期。

#### 报名前必须确认（不可逆，先确认再点）

1. `cloud1-d0gdjckek1de97d07` 绑定在哪个腾讯云账号下？如果小程序没绑腾讯云账号，报名时会**默认用小程序账号新建一个腾讯云账号**。
2. 该环境属于哪种：开发阶段免费体验（→ 自动升级 6 个月个人版）／非开发阶段免费体验（→ 领 120 元代金券）／腾讯云自建环境（**不支持直接选择**，要先转成微信云开发环境）。
3. 环境套餐是「配额制」还是「资源点」？`createModel("cloudbase")` 仅资源点套餐可用；若是配额制，需要先升级套餐，否则调用直接失败。

**这三项都是「点下去就锁定」的动作**：一个小程序只能参与一次，领了就不支持换账号、换环境。

### 方案 B：小程序赞赏组件（P1 · 做）

#### 它带来什么

页面上的「喜欢开发者」按钮，用户点了跳去你的贴图赞赏你，**平台不抽成**。这是文章里唯一「个人主体专属 + 免抽成 + 几乎零开发」的收益通道。

#### 与本项目的关系

退货提醒是典型「小而实用」的工具型小程序，用户用完就走。这类产品最现实的第一笔收入不是订阅费，而是「用过觉得好，赏一点」。赞赏组件正好匹配这种情感路径，且不需要设计付费墙。

#### 技术落点（下一版才动）

1. **先升基础库**：`project.config.json` 的 `libVersion` 从 `3.6.6` 升到 **≥ 3.17.5**，同时在 MP 后台把「最低基础库版本」按要求调整。
2. **组件放哪里**：建议 `miniprogram/pages/settings/settings.wxml` 底部新增一个 `card`。理由：
   - 赞赏是情感动作，不是功能入口，不该占首页看板；
   - 首页是高频操作页，插赞赏按钮会干扰「快速决定退不退」的主任务；
   - 设置页底部天然是「关于这个工具」的位置。
3. **代码自主接入 vs 免开发接入**：选**代码自主接入**。免开发接入每次发版后都要重新接入，对本项目（会频繁发版迭代 OCR）是持续负担。
4. **注意**：单小程序只能一个组件，且组件不传参、不监听事件 —— 页面侧只需放标签，不用写 JS 逻辑。

#### 用户侧动作（AI 做不了）

1. 准备一个贴图号或公众号（本人实名）。
2. 打开「微信开发者助手」小程序 → 赞赏模块 → 选择本小程序 → 点「赞赏」走开通流程。
3. 绑定贴图号 / 公众号。
4. 发表一篇与小程序相关的贴图 —— 建议内容：为什么做这个工具、解决什么痛点、截图展示。**这篇贴图同时是「被看见」的入口**，值得认真写。

#### 四维评估

| 维度 | 结论 |

#### 基础库升级的回归风险（必须先处理）

本项目为兼容低版本积累了一批降级写法，升级后要确认没被破坏：
- WXSS 不用 `:first-child / :last-child / :focus`，改用显式类名 —— 升级后仍成立，但样式可能被新版默认值影响；
- `flex gap` 低版本不生效，已全部用 margin 兜底 —— 升级后 gap 会「开始生效」，**可能与 margin 叠加导致间距翻倍**，这是最可能的视觉回归点；
- `lazyCodeLoading: "requiredComponents"` —— 与新版渲染逻辑需一起验证；
- 毛玻璃 / 背景水印等 `filter`、`backdrop-filter` 用法。

升级后必跑：
- `node scripts/verify-models.js`（485 项纯逻辑）
- `node scripts/verify-project.js`（62 项结构校验）
- 真机验证：首页看板、左滑删除、凭证预览、OCR 回填、设置页保存

### 方案 D：广告（P3 · 延后）

#### 它带来什么

流量主门槛从 500UV 降到 100UV；「广告智能接入」零代码自动推荐位置；「智能变现」页给 ARPU / IPU 对标诊断。

#### 为什么不现在做

1. **门槛是 UV，不是能力**。体验版阶段拿不到 100UV，开了也是零收入。
2. **会破坏已定的视觉风格**。项目已拍板柔彩可爱风（令牌 `--candy-*`），banner 广告是方角、高对比，插进去必然破功。
3. **与产品定位冲突**。这是「用户急着查退货截止日」的工具，页面越干净越好；广告位摆在首页会让核心路径变慢。

#### 真要做，怎么放

- 位置：**只放设置页底部**，用原生模板广告（贴合内容流的观感，比 banner 好看）。
- 首页看板、订单列表、录入页**一律不放**。
- 不开激励视频：本产品没有「看广告换权益」的天然场景，硬造会显得廉价。

#### 四维评估

| 维度 | 结论 |
|---|---|
| 可行性 | 高（零代码可接入） |
| 难度 | 低 |
| 对现有影响 | 中（视觉与体验） |
| 必要性 | 当前为 0（UV 未达门槛） |

**建议：延后。** 触发条件：正式发布并备案完成，且后台近 30 天 UV 稳定超过 100。到那时先只看「智能变现」诊断报告的数，再决定开不开广告位。

### 方案 E：个人主体虚拟支付（P4 · 延后，但有明确启动条件）

#### 它带来什么

真正在小程序内收钱。个人主体、类目含「工具」、认证 + 备案齐全即可申请，月限额 10 万元。

#### 为什么现在不做 —— 核心不是技术，是「没东西可卖」

虚拟支付只支持**道具直购**（`mode: short_series_goods`），必须先在后台【道具管理】建商品、定价格。也就是说，你必须先能回答一个问题：**这个小程序里，什么功能是「免费用户不能用的」？**

当前答案是没有：
- 订单数无上限，所有功能免费；
- 数据只归本人（`uid = openid`），没有多人协作场景；
- 提醒靠应用内名单，没有「付费才能推送」的差异化。

硬造付费墙的风险：
- 这是个人自用型工具，用户对「被卡脖子」极度敏感；
- 一旦有了付费墙，免费版必须**故意变差**，而现在的体验已经打磨过多轮（四级流转、OCR、左滑删除、分页搜索），为了收费去阉割它，是负收益。

#### 什么条件下才启动

满足任一条再启动：
1. 做完了「数据导出 / 报表」（文档里的 F-17），且确认它够复杂、值得收费；
2. 出现了真实的多用户需求（家庭共享、代买代退协作），需要服务端成本；
3. 赞赏的实际收入 ≥ 覆盖认证费（300 元/年）+ 云开发费用，证明有人愿意为它付钱。

#### 一旦启动，技术落点（先记下来，现在不写）

**注意：`cloudfunctions/api` 装不下这套东西**，因为虚拟支付要求「消息推送接收」是一个独立的 HTTP 回调地址。

- 新增云函数 `cloudfunctions/pay/`，三个接口：
  - `POST /pay/order` —— 生成唯一 `outTradeNo`（8–32 位，不能以下划线开头）+ `signData` + `paySig`，返回前端去支付
  - `POST /pay/notify` —— 收 `xpay_goods_deliver_notify`，验签后发货，返回 `<xml><ErrCode>0</ErrCode></xml>`
  - `POST /pay/query` —— 转发 `query_order` 做兜底补发
- 新增集合 `payOrders`：以 `wx_order_id` 做幂等去重（同一订单重复推送只发一次货）
- 前端：`wx.requestVirtualPayment`；iOS 端先校验微信版本 ≥ 8.0.68，不满足时提示升级
- 签名两套，都要按官方文档实现，`post_body` 必须与实际请求体**字节一致**（不格式化、不改键顺序）
- 兜底：定时任务每 5 分钟 `query_order` 查一次未发货订单（可复用 `timerRemind` 的定时触发配置模式，但要另建触发器）
- 金额单位全程用「分」，不换算；`env` 固定填 `0`

#### 定价时必须知道的三件事

1. **iOS 抽 12%**：iOS 用户付 1 元你到手 0.88 元，Android 到手 0.99 元。低价小包（如 1 元/3 元）在 iOS 上性价比很差。
2. **iOS 无法主动退款**：只能用户找 App Store 申请，你控制不了。涉及纠纷时你没有任何处置手段。
3. **iOS 结算 45–60 天**：现金流会比 Android（T+3）慢一个半到两个月。

#### 四维评估

| 维度 | 结论 |
|---|---|
| 可行性 | 中。技术可行，但前置条件多（认证 300 元 + 备案 + 道具设计 + 服务端 3 接口 + 双签名 + 对账） |
| 难度 | 高。是本文四方案里唯一需要新云函数、新集合、新状态机、新对账的 |
| 对现有影响 | 高。涉及新页面（购买）、新数据（订单/权益）、权限判断（免费 vs 付费） |
| 必要性 | **当前低**。没有付费墙，就没有可卖的虚拟道具 |

**建议：延后。** 现在只把前置条件补上（备案、认证可按需），不做代码。

## 八、明确不做的事

避免下一轮把范围做大：

1. **不把腾讯云 OCR 直接删掉。** 双通道并行，AI 只作为新通道和对照，等回归样本证明它稳定后再讨论替换。

4. **不做代币体系。** 官方明确「只做道具直购，不引入代币」。
5. **不动 `uid` 主键原则。** 支付订单、权益表都必须以 `uid` 为主键，`_openid` 只做安全规则。

## 附录 A：本次顺带核实的两处事实更正

这两条不属于文章方法论，但核实时发现，且直接影响现有代码里的**错误文案**，必须单独记一笔。

### A.1 「个人主体不能用订阅消息」是错的 —— 只是不能用「长期订阅」

- 官方口径：个人主体小程序**支持一次性订阅消息**，**不支持长期订阅消息**（长期订阅仅对政务、医疗、交通、金融、教育等线下民生服务类目开放）。
- 现状问题：`miniprogram/pages/settings/settings.wxml` 第 92 行写的是「当前为个人主体小程序，微信暂不支持订阅消息。升级为个体工商户后可开启微信推送」。这句**夸大了限制**。
- 对本项目的实际意义（这才是关键）：
  - 一次性订阅的规则是「用户点一次允许 = 一条下发额度」，额度按**模板 ID** 分格记，且授权必须在用户交互中触发（不能页面一加载就弹）。
  - 放进退货提醒的场景：用户每次录入/编辑订单时弹一次订阅授权，攒额度；到期当天消费一条额度推送。
  - 这会**真正实现「到期微信推送」**—— 也就是产品最初的核心需求，而不只是应用内名单。
- 但这是一项独立功能，工作量不小（要处理额度分格、授权时机、拒收兜底、模板申请），**不与本次变现迁移混在一起排期**。

### A.2 认证不是「可省的 300 元」

- 旧记录写的是「个人主体免认证也能发布」，这句本身没错。
- 但文章提到的虚拟支付要求「**已完成认证和备案**」。所以：
  - 只做赞赏 + 广告 → **不需要认证**；
  - 要做虚拟支付 → **必须认证（300 元/年）+ 备案**。
- 也就是说，那 300 元只在决定收款时才花。别提前花。

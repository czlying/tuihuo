## 0. 记录规则（本次新增的流程约定）

**记录字段**

| 字段 | 含义 |
|---|---|
| date | 具体日期，不写「今天」 |
| target | 提示词 / 函数名 / 正则 / schema |
| version | 规则版本号（见下） |
| changed | 具体改了哪一句规则、哪一段代码 |
| reason | 触发修改的问题 |
| verify | 用哪个样本回测、结果如何 |
| keep_or_revert | 保留 / 待观察 / 回滚 |

**版本号规则**

- 大改结构（输出格式、角色重定义）→ 主版本 +1（v2.0.0、v3.0.0）
- 加规则 / 加字段 → 次版本 +1（v1.1.0、v2.1.0）
- 措辞微调、修 bug → 修订号 +1（v3.0.1、v3.0.2）

**基线**：`v1.0.0` = 2026-10-28 开工前的规则集（`OCR_RULE_VERSION 2026-10-24.2`）。

**只记影响输出的改动**：不记「打开了文件」「改错别字」「重排换行」；
要记新增/删除/调整抽取规则、正则与排除逻辑、标签绑定、schema 字段、误抽 bug 修复。

**两套版本号的关系**：`OCR_RULE_VERSION` / `BUILD_VERSION` 是**部署指纹**（日期制，用于确认云端是否已重传）；
本文件的 `version` 是**规则语义版本**（vX.Y.Z，用于追溯规则演进）。两者在每条记录里并列。

## 6. 验证对照（改前 / 改后 / 是否仍误抽订单号）

**样本**：图1（订单详情页，`订单号：261011-360343170593024`，无「取件码」标签）

改前（旧通道输出，即被填进表单的值）：
```
pickupCode = "261011"   confidence = "low"   needConfirm = true
```

改后（同一样本）：
```
旧通道 pickupCode = ""
新通道 {"platform":"pdd","platform_conf":"high","page_type":"order_detail",
        "has_pickup_code":false,"pickup_code_raw":"","pickup_code_normalized":"",
        "low_confidence":false,"order_sn":"261011-360343170593024",
        "express_company":"","pickup_time":"","address":""}
```

**是否还会误抽订单号 —— 五类变体回测**

| 样本 | 旧通道 pickupCode | 新通道 has | 新通道 raw | order_sn |
|---|---|---|---|---|
| 图1 订单详情页（无取件码标签） | `""` | false | `""` | `261011-360343170593024` |
| 订单号在取件码标签下一行 | `""` | false | `""` | `261011-360343170593024` |
| 取件码与订单号共存 | `"261011"` | true | `"261011"` | `261011-360343170593024` |
| 订单号不带标签裸行 | `""` | false | `""` | `""` |
| 取件码标签 + 数字 593024 | `"593024"` | true | `"593024"` | `""` |

结论：**除「取件码标签下确实有 261011」与「标签下 593024」两条标签绑定场景外，订单号及其任何片段都不会再被抽成取件码**；
第 3 行是需求方给的纠偏示例，取件码与订单号共存时分别取、不混淆。

# 拼多多退货「取件码」页面规则体系

> 2026-10-28 建立。**本文件只建规则，不含代码改动。**
> 用途：给后续 OCR 识别做判据来源；每条规则标注证据等级，样本不足的写「待补充」，不脑补。
>
> **实现契约以 `docs/2026-10-20-OCR平台识别规则手册.md` §15.6/§15.7 为准**；
> 本文件负责「页面/流程规则 + 未观测清单」，schema 以手册为准（§四为设计参考，非当前契约）。
>
> 证据等级：
> - **S（真实样本）**：真实页面全文转录或用户真机截图，可直接作回归用例
> - **A（二手资料）**：教程/攻略文章描述，方向可信、细节需真机复核
> - **B（推断）**：由 S/A 要素组合推出，未在任何单页上观察到
> - **待补充**：无样本，只登记问题，不给结论

## 一、页面类型清单

拼多多退货链路上与「取件码」相关的页面共 11 类。**能出取件码的只有 3 类**（P4/P6/P10），其余页面出码是异常信号。

| # | 页面类型 | 典型标题 / 首行 | 是否出取件码 | 证据等级 |
|---|---|---|---|---|
| P1 | 退货申请成功 / 售后详情（初始态） | `退货退款详情` + `商家处理` | 否 | S |
| P2 | 选择退货方式页 | `请选择退货方式，退回商品` | 否 | S |
| P3 | 上门取件预约页（选时间/地址） | `上门时间` `取件地址` `立即退回` | 否（提交后才生成） | S |
| P4 | **预约成功 / 待取件页** | `预约成功` 或 `待快递员取件` | **是（主战场）** | S |
| P5 | 快递员已接单页 | `快递员：X` + 电话 | 疑是（同 P4 变体） | 待补充 |
| P6 | 取件码展示页 / 取件码弹层 | `取件码` 大字 + `复制` | **是** | 待补充 |
| P7 | 物流详情页（已寄出） | 承运商 + 运单号 + 轨迹 | 否 | 待补充 |
| P8 | 退款进度页 / 退款成功页 | `退款成功` `商家收货` | 否 | 待补充 |
| P9 | 自行寄回 · 填写快递单号页 | `请在N天N小时内填写快递单号` | 否 | S |
| P10 | 急速快寄下单页（平台官方寄件） | `急速快寄` | **是（6 位）** | A |
| P11 | 收货型物流 / 驿站取件页 | `待取件` `菜鸟驿站` `快递柜` | 是，但**语义不同**（取包裹≠寄回） | A |

### 判断依据（关键词 + 模块位置）

判定顺序按「标题 → 状态句 → 操作按钮 → 卡片模块」四层，先命中先定类：

| 页面 | 标题层（顶部） | 状态层（卡片内） | 操作层（底部按钮） | 模块层 |
|---|---|---|---|---|
| P1 | 退货退款详情 | 商家处理中 / 待商家处理 | 撤销售后 | — |
| P2 | 退货退款详情 | 请选择退货方式，退回商品 | 立即退回 / 撤销售后 | 上门取件·去服务点·去快递柜·自行退回 四选卡 |
| P3 | 退货退款详情 | 上门时间 / 取件地址 / 商家地址 | 立即退回 | 快递员取件时，您有什么诉求 |
| **P4** | 退货退款详情 | **预约成功 / 待快递员取件** | 取消预约 / 修改预约 / 撤销售后 | **取件码 + 请在快递员上门后出示**；本次寄件服务享受官方补贴 / 寄件详情 |
| P5 | 退货退款详情 | 快递员将上门取件 + 快递员：X 拨打电话 | 取消预约 / 修改预约 | 同 P4 |
| P6 | 取件码（弹层或独立页） | 取件码 + 复制 | — | 二维码/条码（待补充） |
| P7 | 物流详情 | 运输中 / 派送中 / 已签收 | — | 运单轨迹列表 |
| P8 | 退款详情 | 商家收货 / 退款成功 | — | 退款金额明细 |
| P9 | 退货退款详情 | 请在N天N小时内填写快递单号 | 填写快递单号 | 提示「别把寄件码或取件码填错位置」 |
| P10 | 急速快寄 | 快递员凭取件码上门揽收 | 提交订单 | 发件人/收件人地址卡 |
| P11 | 物流详情 / 取件通知 | 待取件 / 请凭取件码取件 | 一键取件 | 驿站名 / 柜机号 / 隐私号码 |

> 说明：P1–P5 共用同一套「退货退款详情」外壳，区分只靠**状态句**与**卡片模块**。这也是 OCR 最需要靠「组合特征」而非单一关键词的原因。

## 二、每类页面取件码规则

统一回答六问：**是否出现 / 位置 / 形式 / 可复制 / 时效 / 隐藏位数**，并列出同页关联字段。

### P1 退货申请成功 / 售后详情（初始态）

- 是否出现：**否**
- 位置：—
- 形式：—
- 可复制：—
- 时效：—
- 隐藏位数：—
- 同页字段：退货原因、退货地址（商家）、退款金额、进度条（商家处理→寄回商品→商家收货→退款成功）、撤销售后
- OCR 结论：此页无码属**正常**。若 OCR 在此页抽到数字并当取件码 → 判为误识（见风险 R-3）

### P2 选择退货方式页

- 是否出现：**否**
- 位置：四选卡下方无码，只有「上门时间」与「取件地址」
- 形式：—
- 可复制：—
- 时效：—
- 隐藏位数：—
- 同页字段：四种退货方式（上门取件 / 去服务点 / 去快递柜 / 自行退回）、上门时间（如「今天下午都可以（13:00-19:00）」）、取件地址、商家地址、预估费用（￥0 与补贴后价）、月卡专享退货包运费
- OCR 结论：此页**不应**产出取件码；`上门时间` 是相对日期，不应写进取件时间字段

### P3 上门取件预约页

- 是否出现：**否**（提交预约后才生成）
- 位置：—
- 形式：—
- 可复制：—
- 时效：—
- 隐藏位数：—
- 同页字段：上门时间选择器、取件地址（可编辑）、商家地址、快递员诉求备注、预估费用、《拼多多退货服务协议》
- OCR 结论：同 P2。此页《拼多多退货服务协议》是平台判定的强证据（品牌词藏在法务句里）

### P4 预约成功 / 待取件页 ★（取件码主场）

- 是否出现：**是，且必现**
- 位置：**页面中部的独立卡片内**，位于「快递员将上门取件 / 本次寄件服务享受官方补贴」之下、「取件地址」之上；不是按钮旁，也不是顶部
- 形式：**标签行 + 码值行**（`取件码` 单独一行 / 与码同行），码值为**纯数字**；真实样本为 **4 位**（2281、1555）；无条码、无二维码（就真实样本而言）
- 可复制：真实样本未见「复制」按钮（P6 疑有，待补充）
- 时效：与预约时段绑定（如「今天13:00-19:00」）；过期需重新预约，码是否随之变化 —— **待补充**
- 隐藏位数：**不隐藏**，全位显示
- 同页字段：取件码、请在快递员上门后出示、快递员姓名（张宁/郭龙川）、拨打电话、取件地址、取消预约/修改预约、月卡专享·退货包运费、撤销售后
- OCR 结论：**优先级最高**。标签命中即 high；本页即便标签被折叠，也只应在「退货商品」区之前的上半屏找 6 位数字，不可全页乱扫

### P5 快递员已接单页

- 是否出现：疑是（文章描述「快递员凭取件码上门揽收」「快递员会打电话索要取件码」，未取得该页截图）
- 位置：待补充
- 形式：待补充
- 可复制 / 时效 / 隐藏位数：待补充
- 同页字段：快递员：X + 拨打电话、取消预约、修改预约
- OCR 结论：暂按 P4 同构处理（`快递员：` 出现 + 取消预约/修改预约 → 归 P4 变体）

### P6 取件码展示页 / 弹层

- 是否出现：是
- 位置：待补充（疑为大字居中 + 复制组件）
- 形式：待补充（疑有二维码，因为「扫码取件」在快递侧常见）
- 可复制：疑有「复制」
- 时效：待补充
- 隐藏位数：待补充
- OCR 结论：若出现 `复制` 与 `取件码` 邻近，应视为强命中；但**必须先排除**「复制」属于订单号/地址

### P7 物流详情页（已寄出）

- 是否出现：否
- 同页字段：承运商、运单号、轨迹（已揽收/运输中/派送中/已签收）
- OCR 结论：此页应抽**运单号**（express_no），不抽取件码。运单号与取件码混填是 P9 明确警告的错误

### P8 退款进度页 / 退款成功页

- 是否出现：否
- 同页字段：退款金额、退款方式、商家收货、退款成功时间
- OCR 结论：无码；此页能补「退款金额」但不作金额来源（金额应取订单实付）

### P9 自行寄回 · 填写快递单号页

- 是否出现：**否**
- 位置：—
- 同页字段：请在N天N小时内填写快递单号、填写快递单号按钮、退货地址、快递公司选择
- OCR 结论：此页**明确无码**，且页面提示「别把寄件码或取件码填错位置」——这句提示本身是「本页不该出现取件码」的反证。若 OCR 把运单号当取件码填入 → 严重错误

### P10 急速快寄下单页（平台官方寄件）

- 是否出现：是
- 形式：文章称 **6 位取件码**，快递员凭码揽收（A 级证据，无真实样本）
- 位置 / 可复制 / 时效 / 隐藏位数：待补充
- 同页字段：发件人地址、收件人地址（商家退货地址）、快递公司、上门时间、运费
- OCR 结论：与 P4 同类语义（**寄件给快递员的凭证**），可共用标签规则；但位数与 4 位样本冲突，**不可用位数判场景**

### P11 收货型物流 / 驿站取件页

- 是否出现：是，但**语义完全不同**：这是「你去驿站取包裹」的凭证，不是「快递员上门收退货」的凭证
- 位置：物流信息栏 / 取件通知卡片
- 形式：数字，常配合驿站名、柜机号、隐私号码后四位
- OCR 结论：**必须排除**。判据见 R-1 语义消歧

## 三、跨页面通用规则

### R-1 语义消歧：寄件取件码 ≠ 取货取件码（最高优先级规则）

同一句「取件码」在拼多多有两套语义，抽错等于给用户一个没用的码。

| 维度 | 寄件码（本功能要的） | 取货码（必须排除） |
|---|---|---|
| 场景 | 退货寄回，快递员**上门收**你的包裹 | 快递派送，**你去驿站/柜机取**包裹 |
| 强线索 | 快递员将上门取件 / 请在快递员上门后出示 / 寄件详情 / 本次寄件服务享受官方补贴 / 退货商品 / 取消预约·修改预约 | 菜鸟驿站 / 快递柜 / 丰巢 / 派送中 / 请凭取件码取件 / 隐私号码 / 一键取件 / 驿站名 |
| 同页锚点 | 取件地址（你的地址）+ 商家地址 | 驿站地址 / 柜机编号 |
| 结论 | 抽 | 不抽，且标注 `pickup_scene=receive` 让前端提示「这是取包裹的码」 |

判定：寄件线索 ≥1 且取货线索 =0 → `send`；取货线索 ≥1 且寄件线索 =0 → `receive`；两者都有 → `unknown` + need_confirm。

### R-2 出码条件（什么条件下才会出取件码）

```
出码  ⟺  退货方式 ∈ {上门取件, 急速快寄}
        且 已完成预约（预约成功 / 待快递员取件 / 快递员已接单）
        且 快递员尚未取走（取走后退款进度页无码）
不出码 ⟺  退货方式 ∈ {去服务点, 去快递柜, 自行寄回(手填单号)}
        或 尚未选退货方式（P1）
        或 已寄出/已签收（P7/P8）
```

- 证据：P2 四选含「去服务点/去快递柜/自行退回」（S）；P9 手填单号页无码且警告别填错（S）；P10 急速快寄有码（A）。
- **待补充**：去服务点 / 去快递柜两种方式是否也有自己的取件凭据（如服务点单号、柜机码）——目前无样本，不结论。

### R-3 位数不固定，禁止用位数判场景

- 真实样本：**4 位**（2281、1555）
- 文章描述：**6 位**（急速快寄、部分教程）
- 规则：取值只认「标签命中」或「邻近标签的纯数字」，**不设位数上下限做判定**；位数只作为 `pickup_code_digits` 字段输出，供核对
- 影响：现有兜底正则 `\b\d{6}\b` 只覆盖 6 位，无标签页面的 4 位码会漏抽（见风险 R-7）

### R-4 标签优先，标签集固定

标签：`取件码`、`取件号`、`上门取件码`、`寄件码`。
命中即 high，不需要其他证据。标签后同行取值优先，其次取下一行。
反例排除：标签下一行若是说明句（`请在快递员上门后出示`、`请向快递员出示`），不是码值，此时应继续在同一行找数字或走邻近兜底。

### R-5 兜底只在寄件场景、且只在上半屏

- 前提：R-1 判为 `send`（或至少非 `receive`）
- 范围：**从页面顶部到「退货商品」区之前**（P4 实际位置在上半屏），不在全页扫
- 只取离「取件码」标签行最近的纯数字；距离相同取靠前
- 结果一律 `low` + `need_confirm=true`，必须让用户核对
- 禁止：把运单号（12–18 位连续数字）、订单号、手机号尾号、门牌号当取件码

### R-6 时效与预约时段绑定

- 取件码对应一次预约（时段如「今天13:00-19:00」「明天09:00-11:00」）
- 过期需重新预约（A 级描述）；重新预约后码是否变化 —— **待补充**
- 规则：OCR 只抽码与时段原文，**不做时效推断**；前端可展示「预约时段」原文，由用户判断是否过期

### R-7 快递公司差异

| 寄件方式 | 承运方 | 取件码 | 证据 |
|---|---|---|---|
| 上门取件（平台补贴） | 文章称顺丰承接，平台补贴价 | 有，4 位（真实样本） | S + A |
| 急速快寄 | 中通/圆通/韵达等 | 有，6 位 | A |
| 自行寄回（自选快递） | 用户自选（顺丰/中通/菜鸟驿站等） | **无**，只有运单号 | S |

- 规则：**取件码格式不随快递公司变化**（无法从样本观察到差异），判定只看场景与标签，不看承运商名
- 待补充：顺丰/通达系各自 App 内的取件码与拼多多页展示是否一致

### R-8 OCR 易误识位置（按风险排序）

1. **「取件码」四个字本身**：标签文案与码值在同一行时，OCR 可能把「取件码2281」当一整串，需要按标签切分
2. **4 位数字与时间/金额混淆**：`2281`、`1555` 这类 4 位数，与 `13:00`、`￥0`、`¥5.03`、门牌号 `23号楼4单元6层461` 形近；缺标签时极易抽错
3. **取件地址里的数字**：`2001号`、`23号楼`、`4单元`、`6层461`——绝不能进码
4. **手机号后四位**：P11 取货场景用「手机尾号后四位」取件，与取件码同形
5. **运单号**：12–18 位连续数字，P9 明确要求别混填
6. **「复制」按钮归属**：`复制` 可能属于订单号、地址、取件码三者任一，不能仅凭邻近 `复制` 判定

## 四、OCR 抽取字段 schema

> ⚠️ 本节是**设计参考表**（含当时设想的 `pickup_scene`、`express_no` 等）。
> 当前实现只输出 11 个字段，以手册 §15.6 为准；本文 §六 记录了哪些设想已落地、哪些未做。


面向云函数 `ocrOrder` 的返回结构。`现状` 列：**已有** = 当前代码已输出；**待加** = 本轮规则暴露出需要但尚未实现（不在本轮改）。

| 字段 | 类型 | 取值 / 说明 | 现状 | 依据 |
|---|---|---|---|---|
| `page_kind` | enum | `aftersale_detail` / `order_detail` / `unknown` | 已有 | P1–P9 共用售后外壳 |
| `pickup_scene` | enum | `send`（寄件码）/ `receive`（取货码）/ `unknown` | **待加** | R-1 |
| `pickup_code` | string | 码值，纯数字或数字+字母；无则 null | 已有 | R-4 |
| `pickup_code_digits` | int | 码长度（4/6/其他），仅作核对，不参与判定 | **待加** | R-3 |
| `pickup_code_source` | enum | `label` / `regex` / `''` | 已有 | R-4 / R-5 |
| `pickup_code_confidence` | enum | `high` / `low` / `''` | 已有 | R-4 |
| `need_confirm` | bool | `confidence !== 'high'` | 已有 | 既有闸门 |
| `pickup_window_text` | string | 预约时段原文，如「今天13:00-19:00快递员将上门取件」 | 部分（现塞在 `pickupTime`） | R-6 |
| `pickup_window_date` | string | `YYYY-MM-DD`，仅当原文含绝对日期才填；相对日期留空 | **待加** | R-6 |
| `ship_method` | enum | `上门取件` / `急速快寄` / `去服务点` / `去快递柜` / `自行寄回` / `''` | **待加** | R-2 |
| `courier_name` | string | 快递员姓名（`快递员：X`） | **待加** | P4/P5 |
| `pickup_address` | string | 取件地址（用户地址侧） | **待加** | P2–P4 |
| `merchant_address` | string | 商家地址（退货地址侧） | **待加** | P2/P3 |
| `express_no` | string | 运单号（寄出后才有） | **待加** | P7/P9，且与取件码互斥 |
| `order_no` | string | 订单号 | 已有 | 既有 |
| `return_no` | string | 退货/售后单号 | 已有 | 既有 |
| `platform` / `platform_confidence` | string / enum | `拼多多` + `high`/`medium`/`unknown` | 已有 | 见要素文档 |
| `raw_lines` | string[] | OCR 原始行，供人工复核与回归 | 已有 | 既有 |
| `rule_version` | string | 规则版本号 | 已有 | 既有 |

互斥约束（重要）：
- `pickup_code` 与 `express_no` **不应同时非空**：前者是待取件，后者是已寄出
- `pickup_scene=receive` 时 `pickup_code` 应强制置空并给提示，不得写入订单
- `pickup_code_digits` 仅展示，不参与任何「是不是取件码」的判定

## 五、自验证结果 + 风险点

### 5.1 样例回归（用当前线上规则跑，未改代码）

| 样例 | 页面 | 取件码 | 置信度/来源 | 其他字段表现 |
|---|---|---|---|---|
| A 用户真机截图（2281） | P4 预约成功 | `2281` ✅ | high / label | 商品名空 ✅、金额 0 ✅、平台 unknown（该页无品牌词，符合规则） |
| B 网络转录预约成功页（1555） | P4 预约成功 | `1555` ✅ | high / label | **商品名错误**：`拨打电话取消预约` ❌ |
| C 网络转录选择退货方式页 | P2 | 空 ✅（本页本就无码） | — | **商品名错误**：`去服务点` ❌；**取件时间错误**：`今天下午都可以（13:00-19:00）` 被填入 ❌ |

结论：**取件码抽取在两份真实页面上都稳定命中（2/2）**，符合「标签命中即 high」的规则；缺陷集中在商品名与取件时间，不影响取件码本身。

### 5.2 规则覆盖不到 / 易错（按严重度）

| # | 问题 | 触发条件 | 影响字段 | 现状 |
|---|---|---|---|---|
| R-7 | 4 位码在**无标签**页面会漏抽 | 页面只有 `2281` 没有「取件码」三字 | `pickup_code` | 兜底正则只认 6 位 |
| R-9 | 商品名抽到按钮/方式卡文案 | 页面含 `拨打电话`、`取消预约`、`去服务点` | `product_name` | 已过滤部分，仍有漏（本次 B/C 样本实证） |
| R-10 | 相对日期写进取件时间 | 标签 `上门时间：今天下午都可以…` | `pickup_time` | 相对日期拦截只加在句子兜底，标签路径未拦 |
| R-11 | 取货码与寄件码无法区分 | 截图混入收货物流页 | `pickup_code` | 缺 `pickup_scene` 字段 |
| R-12 | 运单号可能被当取件码 | P9/P7 页面出现 12–18 位数字 | `pickup_code` | 无 `express_no` 互斥约束 |
| R-13 | 平台仍判不出 | P4/P2 页无品牌词 | `platform` | 见要素文档，待定判定通道 |
| R-14 | 时效无法判断 | 码已过期但 OCR 照抽 | — | 按设计不推断，前端提示时段原文 |
| R-15 | P5/P6/P7/P8/P10/P11 无真实样本 | — | 相关字段 | **待补充**，本轮不给规则结论 |

### 5.3 OCR 优先级最高的页面

1. **P4 预约成功 / 待取件页 —— 最高**。唯一「必现取件码 + 位置固定 + 标签稳定」的页面，也是用户真正需要抄码的时刻。规则收益/成本比最高，应作为第一优先与回归基线。
2. **P6 取件码弹层 —— 次高**（疑有复制/二维码，命中即 high），但缺样本，无法现在定规则。
3. **P10 急速快寄下单页 —— 第三**，语义同为寄件码，但位数 6 位、无真实样本。
4. **P1/P2/P3/P9 —— 反向价值**：这些页面**不应该**出码，是「防误抽」的负样本，价值等同正样本。
5. **P11 —— 必须排除**，否则给出的是取包裹的码，用户拿去给快递员会当场对不上。

### 5.4 建议的下一步（本轮不做）

- 补 6 类页面真实截图（P5/P6/P7/P8/P10/P11），优先 P6 与 P11：一个定正样本，一个定负样本
- 规则落地顺序建议：`pickup_scene` 语义消歧（R-1）→ 兜底放宽到 4–6 位且限定上半屏（R-7/R-5）→ 商品名与相对日期两处修补（R-9/R-10）→ 平台判定通道（R-13）
- 每条规则落地都要带真实页回归用例，并做可证伪校验
